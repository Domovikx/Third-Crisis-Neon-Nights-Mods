# Аудит: где Rust даёт профит, а где остаётся TS

Дата: 2026-11-22. Основание: решение владельца и куратора — стек проекта **TS + Rust**,
языки равнозначны, выбор по **измеримому профиту**, Python запрещён (правило — в `AGENTS.md`,
раздел «Языки»).

Документ живой: при появлении новых замеров или новых задач аудит пересматривается, решение
фиксируется здесь же.

## Как измеряем профит

Профит считается только по трём осям, каждая должна быть наблюдаемой:

- **скорость** — wall time на реальной нагрузке (не синтетика), с профилем по фазам;
- **ресурсы** — пиковая память (RSS), размер артефакта, время старта;
- **возможность** — TS объективно не умеет (нет библиотеки, нужен бинарный формат/рантайм).

**Профит считаем в процентах, а не в секундах** (решение владельца 2026-11-22). Абсолютные
секунды обманчивы: QA на 7 МБ — 310 мс, но тот же код на корпусе в 300 МБ — ~15 с в каждом
прогоне. Поэтому замер — **МБ/с и относительный прирост**, с прицелом на будущий масштаб
(следующие игры-новеллы дадут объёмы на порядок больше).

**Порог предложения миграции — прирост ≥ 10 %** на реальной нагрузке. Это основание поставить
вопрос, но решение принимается после оценки **стоимости переноса** и согласования с владельцем:
10 % — порог предложения, а не автоматического переезда. Кайдзен = измерить → предложить →
согласовать → перенести.

## Вердикты по компонентам

### Rust — оправдан

- **Ядро дампера Unity** (`unityfs`, `serialized`, `rawscan`). Работа с байтами, смещениями и
  декомпрессией: плотный CPU-путь, где компилятор ловит класс ошибок (границы, переполнения), а
  память предсказуема. Замер TS: полный дамп 150 с, из них 11 с — контейнеры, ~139 с — извлечение
  и сериализация. Сравнение с Rust ведётся задачей `dual-dumper-ts-rust`; решение — по её цифрам.
- **FSB5 + Vorbis для студийных голосов.** Capability gap: все 7 715 `AudioClip` в игре —
  Vorbis внутри FSB5, зрелого TS-декодера с заголовками FMOD нет. Профит: разблокирует
  извлечение референсов для клонирования голоса (продуктовая задача).
- **Tauri для GUI инсталлятора/мод-менеджера** (если GUI понадобится). Ресурсный профит:
  маленький бинарь и низкая память против Electron. Сейчас не начинаем — нет GUI-требования.

### TS — остаётся

- **Пайплайн POT/PO** (`potgen`, `po2dat`, `inventory`, `po_update`, `prefill_po`,
  `find_source`). Текст и JSON; прогон 1–3 с на 319 МБ дампа, раз на апдейт игры. Профит Rust
  не измерим на фоне задачи.
- **QA и ревью** (`qa_translate`, `review_queue`). Секунды, HTML-отчёт, экосистема.
- **Пакетный перевод** (`translate_local`). Ждёт ответа LLM — I/O-bound, язык не влияет.
- **Сборка и деплой** (`build`, `build_proxy`, `deploy`). Обёртки над `csc.exe`/`cl.exe` и
  копирование файлов — I/O.
- **Инсталлятор CLI** (`installer/install.mts`). Тонкая обёртка над деплоем; ресурсы неважны.
- **Сайт** (`scripts/build_site.mts`). Генерация одного HTML.
- **Харнессы** (`dump_parity`, `dump_bench`). Оркестрация внешних процессов и сравнение данных.

### Запрещено / выводится

- **Python** — запрещён и **удалён 2026-11-22**: `dump_assets.py`, `requirements.txt` и py-джоб CI
  убраны после доказанного паритета. Оракул теперь — взаимная сверка TS ↔ Rust и контрольные суммы.
- **PowerShell** — не развиваем. `package_release.ps1` (упаковка релиза) подлежит порту на TS:
  это I/O и архивы, Rust тут не даёт профита.

## Триггеры пересмотра

- Появился замер, показывающий **≥2x** на пути, который выполняется регулярно → переводим на Rust.
- Участок перестал быть горячим (например, дамп стал запускаться чаще/реже) → пересматриваем.
- Появилась зрелая TS-библиотека под задачу, которую закрывал Rust по capability gap → допустим
  обратный перевод, если качество и поддержка не хуже.
- Любое решение фиксируется здесь с цифрой и датой; «на Rust быстрее» без замера — не основание.

## Замеры-отказы (проверено, миграция не нужна)

- **QA (`qa_translate`) — 267 мс на язык, 2.0 с на все 10** (2026-11-22, замер `time`,
  данные: 5.8 МБ `.dat` + 22 МБ `po/`). Rust сэкономит ~1.5 с на полный прогон раз в день —
  это не профит по нашим критериям. Остаётся на TS.
  Пересмотр: если QA начнёт бегать в CI на каждый коммит, или появится сплошной ML-прогон
  по корпусу, или объёмы вырастут на порядок.
- **`po2dat` — ~0.5–2 с на язык** (10 тыc. строк). Rust не нужен по той же причине.
- **`potgen` — 3.2 с на 319 МБ дампа** (против 31 с у Python). Уже достаточно быстро: это раз
  на апдейт игры. Быстрым оказался не язык, а отказ от перебора `dir()` на каждом объекте.

## Пересмотр: QA в процентах (2026-11-22)

Аргумент владельца: секунды на маленьком проекте обманчивы — важны **проценты**, потому что
следующие игры (новеллы) дадут объёмы на порядок больше. Замеры для решения:

- QA (TS): 310 мс на язык, из них 57 мс — старт Node; входы 7 МБ.
- Чистый парсинг PO в TS: **57 МБ/с**.
- Прогноз: ×10 данных → ~1.5 с, ×100 (крупная новелла) → ~15 с в TS.

Поэтому открыт спайк `tasks/2026-11-22-rust-qa-spike.md`: реализация QA на Rust, паритет
находок побайтово и замер масштабирования на 1×/10×/100× синтетики. Решение — по коэффициенту,
а не по абсолютному времени.
