# Аудит: где Rust даёт профит, а где остаётся TS

Дата: 2026-11-22. Основание: решение владельца и куратора — стек проекта **TS + Rust**,
языки равнозначны, выбор по **измеримому профиту**, Python запрещён (правило — в `AGENTS.md`,
раздел «Языки»).

Документ живой: при появлении новых замеров или новых задач аудит пересматривается, решение
фиксируется здесь же.

## Как измеряем профит

Профит считается только по трём осям, каждая должна быть наблюдаемой:

- **скорость** — wall time на реальной нагрузке (не синтетика), с профилем по фазам;
- **ресурсы** — пиковая память (RSS), размер артефакта, время старта;
- **возможность** — TS объективно не умеет (нет библиотеки, нужен бинарный формат/рантайм).

**Профит считаем в процентах, а не в секундах** (решение владельца 2026-11-22). Абсолютные
секунды обманчивы: QA на 7 МБ — 310 мс, но тот же код на корпусе в 300 МБ — ~15 с в каждом
прогоне. Поэтому замер — **МБ/с и относительный прирост**, с прицелом на будущий масштаб
(следующие игры-новеллы дадут объёмы на порядок больше).

**Порог предложения миграции — прирост ≥ 10 %** на реальной нагрузке. Это основание поставить
вопрос, но решение принимается после оценки **стоимости переноса** и согласования с владельцем:
10 % — порог предложения, а не автоматического переезда. Кайдзен = измерить → предложить →
согласовать → перенести.

## Вердикты по компонентам

### Rust — оправдан

- **Ядро дампера Unity** (`unityfs`, `serialized`, `rawscan`). Работа с байтами, смещениями и
  декомпрессией: плотный CPU-путь, где компилятор ловит класс ошибок (границы, переполнения), а
  память предсказуема. Замер TS: полный дамп 150 с, из них 11 с — контейнеры, ~139 с — извлечение
  и сериализация. Сравнение с Rust ведётся задачей `dual-dumper-ts-rust`; решение — по её цифрам.
- **FSB5 + Vorbis для студийных голосов.** Capability gap: все 7 715 `AudioClip` в игре —
  Vorbis внутри FSB5, зрелого TS-декодера с заголовками FMOD нет. Профит: разблокирует
  извлечение референсов для клонирования голоса (продуктовая задача).
- **Tauri для GUI инсталлятора/мод-менеджера** (если GUI понадобится). Ресурсный профит:
  маленький бинарь и низкая память против Electron. Сейчас не начинаем — нет GUI-требования.

### TS — остаётся

- **Пайплайн POT/PO** (`potgen`, `po2dat`, `inventory`, `po_update`, `prefill_po`,
  `find_source`). Текст и JSON; прогон 1–3 с на 319 МБ дампа, раз на апдейт игры. Профит Rust
  не измерим на фоне задачи.
- **QA и ревью** (`qa_translate`, `review_queue`). Секунды, HTML-отчёт, экосистема.
- **Пакетный перевод** (`translate_local`). Ждёт ответа LLM — I/O-bound, язык не влияет.
- **Сборка и деплой** (`build`, `build_proxy`, `deploy`). Обёртки над `csc.exe`/`cl.exe` и
  копирование файлов — I/O.
- **Инсталлятор CLI** (`installer/install.mts`). Тонкая обёртка над деплоем; ресурсы неважны.
- **Сайт** (`scripts/build_site.mts`). Генерация одного HTML.
- **Харнессы** (`dump_parity`, `dump_bench`). Оркестрация внешних процессов и сравнение данных.

### Запрещено / выводится

- **Python** — запрещён и **удалён 2026-11-22**: `dump_assets.py`, `requirements.txt` и py-джоб CI
  убраны после доказанного паритета. Оракул теперь — взаимная сверка TS ↔ Rust и контрольные суммы.
- **PowerShell** — не развиваем. `package_release.ps1` (упаковка релиза) подлежит порту на TS:
  это I/O и архивы, Rust тут не даёт профита.

## Триггеры пересмотра

- Появился замер, показывающий **≥2x** на пути, который выполняется регулярно → переводим на Rust.
- Участок перестал быть горячим (например, дамп стал запускаться чаще/реже) → пересматриваем.
- Появилась зрелая TS-библиотека под задачу, которую закрывал Rust по capability gap → допустим
  обратный перевод, если качество и поддержка не хуже.
- Любое решение фиксируется здесь с цифрой и датой; «на Rust быстрее» без замера — не основание.

## Пересмотр: QA в процентах (2026-11-22)

Аргумент владельца: секунды на маленьком проекте обманчивы — важны **проценты**, потому что
следующие игры (новеллы) дадут объёмы на порядок больше. Замеры для решения:

- QA (TS): 310 мс на язык, из них 57 мс — старт Node; входы 7 МБ.
- Чистый парсинг PO в TS: **57 МБ/с**.
- Прогноз: ×10 данных → ~1.5 с, ×100 (крупная новелла) → ~15 с в TS.

Спайк выполнен: QA на Rust даёт **2.6–3.7×** при побайтовом паритете находок (ru 1 684,
de 729) и на 100× не упирается в память. **Решение: вычислительное ядро QA — на Rust, HTML-отчёт
остаётся в TS** (`npm run qa` = Rust → JSON → HTML; `npm run qa:ts` — эталон-оракул).
Таблица масштабирования и условия пересмотра — `docs/qa-scaling.md`.

## Замеры текстового пайплайна (2026-11-22)

- `potgen` (+ `inventory`): **1 889 мс на 95 МБ дампа ≈ 50 МБ/с** → кандидат на Rust (ожидаемо
  2–3×). Задача: `tasks/2026-11-22-rust-text-core.md`.
- `po2dat`: **712 мс** на ~5.3 МБ PO ≈ 7.5 МБ/с (на 10 языках ~7 с) → кандидат; парсер PO уже
  есть в Rust (`tools/rust-qa`), поэтому первым шагом — общий крейт.
- `build:site` (1 412 мс) и `build`/`deploy` (копирование, `csc`/`cl`) → **остаются на TS**:
  это UI и оркестрация, профита нет.
- `qa` — уже на Rust (2.6–3.7×, `docs/qa-scaling.md`).
- Дампер — уже на Rust (3.0× на байтах, `docs/rust-vs-ts.md`).

Правило распределения, итог: **Rust — вычисления с плотными данными; TS — UI, оркестрация,
эталоны и всё, что не даёт 10 %.**

## Пересмотр: `potgen` и `po2dat` → Rust (2026-11-22)

Основание: задача `tasks/2026-11-22-rust-text-core.md`; прошлые «замеры-отказы» выше
(`po2dat — 0.5–2 с`, `potgen — 3.2 с`) смотрели на абсолютные секунды и на этом замере
пересмотрены по правилу «проценты, а не секунды».

Что сделано: общий крейт `tools/rust-l10n-core` (`po`/`dat`/`json`, из `tools/rust-qa`)
и бинарь `tools/rust-l10n` с подкомандами `potgen`/`po2dat`. TS-реализации остаются
эталонами-оракулами (`potgen:ts`, `po2dat:ts`), паритет — гейт `scripts/text_parity.test.mts`.

### Методика

- Точки: `potgen` (JSONL-дамп → POT) и `po2dat` (`template.pot` + `po/<lang>.po` → `.dat`).
- Объёмы: **1×** — реальный дамп `tmp/dump-new` (94.0 МБ, 149 файлов) и реальные
  `po/template.pot` + `po/ru.po` (5.3 МБ); **10×** — синтетика в `tmp/text-bench/`:
  10 копий дампа, у каждой текстовые поля (`dialogues[].text`, `raw_strings`, `fsm_strings`,
  `settings_keys[].display`) получают суффикс `~k`, плюс 10× POT/PO с суффиксом в
  `msgid`/`msgctxt` — ключи не схлопываются, каталог и выход растут вместе с входом.
- Каждый инструмент — **отдельным процессом** (`spawnSync`), wall time включает старт
  рантайма; два прогона на точку (холодный/прогретый кэш ФС); МБ/с — по второму.
- Гейт: выходы TS и Rust на каждой точке сравниваются **побайтово** (POT пишется с
  фиксированной датой `--created`).
- Воспроизведение: `cargo build --release --manifest-path tools/rust-l10n/Cargo.toml`,
  затем `node scripts/text_bench.mts --scales 1,10 --runs 2`.
- Машина: Windows 11, Ryzen 7 7800X3D, 32 ГБ RAM, NVMe; Node 24.20; Rust 1.100
  (release, `lto=true`, `codegen-units=1`).

### До/после (TS → Rust)

| Точка         | Вход, МБ | TS, мс (1/2)    | Rust, мс (1/2) | × (1/2)     | TS, МБ/с | Rust, МБ/с | Паритет |
| ------------- | -------- | --------------- | -------------- | ----------- | -------- | ---------- | ------- |
| potgen 1×     | 94.0     | 1 547 / 1 543   | 775 / 758      | 1.99 / 2.03 | 60.9     | 123.9      | ✓       |
| potgen 10×    | 860.9    | 14 489 / 14 526 | 8 315 / 8 167  | 1.74 / 1.78 | 59.3     | 105.4      | ✓       |
| po2dat 1× ru  | 5.3      | 305 / 312       | 69 / 65        | 4.40 / 4.76 | 17.0     | 80.8       | ✓       |
| po2dat 10× ru | 56.2     | 2 360 / 2 337   | 743 / 791      | 3.17 / 2.96 | 24.1     | 71.1       | ✓       |

Сырые числа — `tmp/text-bench/results.json` (в git не попадает).

Разброс между полными прогонами стенда — единицы процентов (второй полный прогон дал
1.98–2.01× / 1.75–1.76× для `potgen` и 3.3–4.4× для `po2dat`). Выводы — по диапазону, а
не по одной цифре.

### Что это значит

- **`po2dat` — 3.0–4.8×** и ровно тот же `.dat` на всех 10 языках репозитория: парсер PO
  был узким местом, в Rust он переиспользуется из общего крейта. Миграция оправдана с
  запасом.
- **`potgen` — 1.74–2.03×**: на реальном дампе ~2× (порог миграции), на 10× просадка до
  1.74–1.78× (растёт каталог и выход, а не только парсинг). Пропускная способность TS
  упирается в ~60 МБ/с, Rust идёт 105–124 МБ/с. Это выше порога предложения (10 %) почти
  в 20 раз;
  порог «миграция ради скорости ≥ 2×» выполняется на текущей нагрузке и почти выполняется
  на прогнозной — решение: **мигрируем, TS остаётся оракулом**.
- Ускорение `potgen` получено не «голым языком»: serde разбирает только 8 нужных полей
  строки, остальное (`fields`, type trees) пропускается без аллокаций. Первая версия на
  `serde_json::Value` давала ≈91–94 МБ/с (≈1.5×) — цифра до/после поймана замером, а не на
  глаз.
- Пик памяти отдельно не инструментирован (в задаче требовались время и МБ/с).

### Условия пересмотра

1. Коэффициент `potgen` упадёт ниже 1.5× (например, TS получит потоковый парсер) —
   вернуться на TS по тому же правилу.
2. Формат POT/PO начнёт меняться чаще, чем раз в релиз, — цена второй реализации и
   паритета перевесит выигрыш.
3. Появится инкрементальный режим (дельта вместо полного прохода) — пересмотреть границу:
   возможно, Rust должен читать только изменённые чанки.

## Пересмотр: `po_update`, `prefill`, `find_source` → Rust (2026-11-22)

Основание: задача `tasks/2026-11-22-rust-po-update.md`. Вердикт выше («пайплайн POT/PO —
`po_update`, `prefill_po`, `find_source` — остаётся на TS») **пересмотрен** по тому же правилу,
что и QA: он смотрел на абсолютные секунды одного прогона, а не на пропускную способность.
Решающий аргумент — DRY: `tools/rust-l10n-core` уже нёс парсер/рендер PO, а `po_update` держал
свой TS-парсер; теперь парсер ОДИН на весь пайплайн (`potgen`, `po2dat`, `po_update`, `prefill`,
`find_source`).

Что сделано: подкоманды `po_update` (с починкой учёта выпавших ключей), `prefill`,
`find_source` на общем крейте. TS-реализации остаются оракулами: `po:update:ts`,
`po:prefill:ts`, `find:source:ts`; паритет — гейт `scripts/text_parity.test.mts`.

### Методика

- Точки: `po_update`, `prefill` (`template.pot` + `po/ru.po`) и `find_source` (скан дампа).
- Объёмы: **1×** — реальные `po/template.pot` + `po/ru.po` (5.3 МБ) и реальный дамп
  `tmp/dump-new` (94.0 МБ); **10×** — синтетика `tmp/text-bench/po2dat-10x/` (те же POT/PO с
  уникальными ключами `~k`, 56.2 МБ).
- Каждый инструмент — отдельным процессом; round-trips идемпотентны, поэтому копия входа
  сбрасывается перед каждым прогоном **вне** замера. Два прогона на точку, МБ/с — по второму.
- Гейт: выходы сравниваются **побайтово** (`po/<lang>.po`, вывод `find_source`), а не «почти».

| find_source 1× (дамп) | 94.0     | 1 386 / 1 462 | 688 / 709      | 2.02 / 2.06 | 64.3     | 132.6      | ✓       |

Воспроизведение: `npm run l10n:build`, затем `node scripts/text_bench.mts --scales 1,10 --runs 2`

### Замер поймал две вещи (кайдзен)

- Первая версия `po_update` дала всего **2.1–2.4×** при 36 МБ/с: `merge` занимал 73 мс из 140 —
  клонирование пары строк на каждый ключ (в карту, в `HashSet`, в поиск). Ключи стали
  заимствованными (`&str`), `merge` упал до 24–33 мс.
- `render` занимал 25 мс из 80: `format!` на каждую из ~200 тыс. строк. Один буфер вместо
  `format!` + `join` — 5–8 мс. Итог: 90–100 мс против 374–415 у TS.
- Урок для протокола: замер «до/после» надо делать **после** профиля, иначе решение о миграции
  принимается по неоптимизированному коду (и наоборот — «Rust в 2× быстрее» без профиля
  занижает выигрыш).

### Учёт выпавших ключей (новое поведение, а не только язык)

Именно `po_update` породил 1 321 мёртвый перевод (`docs/data-audit.md` §5.3) и молчал об этом.
Теперь отчёт (stderr) печатает `carried`, `new`, `obsolete`, `retargeted`, `legacy_kept`,
`orphans`, `dropped`, `dup_keys`; `--json <path>` пишет полный список (не «первые 10»):

- `orphans` — записи PO, чьего ключа нет в POT (сегодня **1 321**: 666 ru, 324 de, 324 pl, по 1
  остальным — ровно цифра из аудита). Это не «потерянные переводы», а мёртвые: рантайм их
  пропускает по `sk`, но они видны поимённо и их можно вернуть в POT или удалить;
- `dropped` — переводы, которым в этом прогоне некуда деться (текст жив под уже переведённым
  контекстом — те 48 групп, или два исчезнувших ключа претендовали на один). Печатается
  `WARNING` со списком и «где текст жив»; байты PO не меняются (паритет);
- `dup_keys` — ключ записан в PO несколько раз: выбор фиксируется правилом (`--dup-rule`,
  по умолчанию `last` = поведение TS/`msgmerge`; `earliest-ref` = то, что увидит рантайм) и
  **сообщается** с обоими вариантами.

Выход по-прежнему байт-в-байт равен TS-эталону на всех 10 языках: отчёт — отдельный канал,
решение о судьбе мёртвых строк принимает человек (`tasks/2026-11-22-data-integrity-lint.md`).

### Условия пересмотра

1. `po_update`/`prefill` упадут ниже 2× на реальных объёмах (например, TS получит потоковый
   парсер) — вернуться на TS по тому же правилу.
2. Появится инкрементальный режим (дельта вместо полного прохода) — пересмотреть границу.
3. `prefill` живёт только как исторический вход (`translations/` в репе нет): если легаси-корпус
   объявят ненужным, `prefill` уходит целиком, а не чинится.
