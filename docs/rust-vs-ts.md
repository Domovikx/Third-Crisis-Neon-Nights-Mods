# Rust против TypeScript на реальной задаче: дамп Unity-ассетов

Документ отвечает на один вопрос: **что даёт Rust там, где TypeScript уже работает** —
на настоящем корпусе (163 файла игры Third Crisis: Neon Nights, 2.18 ГБ, 507 415
объектов, 86.6 МБ итогового JSONL). Замеры воспроизводимы одной командой, цифры
приведены двумя прогонами, паритет выхода проверяется побайтово.

> Снимок 2026-11-22. После снятия обрезок в дампе (`docs/dump-losses.md`) корпус даёт
> 578 474 объекта и 134 МБ JSONL, `--decoder rust` — 64 с вместо 57: выросла фаза
> сборки (больше строк на запись). Отношение Rust/TS на байтовом уровне не изменилось.

> **Состояние 2026-11-24 (важнее таблиц ниже).** TS-реализации, с которыми сняты эти
> замеры, **удалены** (коммит `7f170cb`, решение владельца «всё TS-легаси выпиливаем»):
> декодер, сборка дампа, QA-ядро, `potgen` и `po_update` живут только на Rust. Таблицы
> ниже — **исторический замер**, воспроизвести его уже нельзя. Оракул теперь —
> **золотые фикстуры** (`test_data/` + `sha256` выходов, см. §14). Команды `dump:ts`,
> `qa:ts`, `potgen:ts`, `po:update:ts`, а также стенды `dump_parity` и `dump_bench`
> больше не существуют.

## 1. Что именно сравнивается

Обе реализации решают ОДНУ задачу и выпускают ОДИН промежуточный формат (rd1) —
поэтому сравнение честное: не «TS против пустоты», а два исполнителя одного
контракта на одном наборе файлов.

| Вариант     | Что делает                                                     |
| ----------- | -------------------------------------------------------------- |
| `ts`        | полный TS-дампер: байты → семантика → JSONL (`dumpAssets`)     |
| `rust`      | Rust-декодер (байты → rd1) + тот же TS-сборщик итогового дампа |
| `ts-core`   | только байтовый уровень на TS: пишет rd1 (`writeRawDumpTs`)    |
| `rust-core` | только Rust-декодер: пишет rd1 (`rust-decoder dump`)           |

`ts` = `ts-core` + сборка дампа, поэтому фазы TS-пути видны из `ts-core`
(чтение/декомпрессия/сканы/печатные строки) и из `assemble` варианта `rust`
(сборка итогового JSONL). Для `ts` фазы отдельно не инструментированы — там
байты и семантика внутри одного вызова, и врать «фазовыми» числами не нужно.

Побочный, но более важный результат: вторая реализация — это **оракул**.
Компилятор проверяет типы и память, но не смысл; паритет rd1 побайтово на
реальном корпусе проверяет смысл и ловит регрессии сразу в обеих реализациях.
Именно поэтому Rust-путь оставлен в проекте как рабочий вариант (`--decoder rust`),
а не как одноразовый эксперимент.

## 2. Граница: байты в Rust, каталожная логика в TS

Rust делает то, что является работой с байтами, и НЕ знает, «что попадёт в POT»:

- контейнер UnityFS: разбор заголовка/blocksInfo/entry, LZ4 и LZMA;
- SerializedFile v22: заголовок, type table, object table, externals, скрипты;
- сырые сканы объектов: печатные ASCII-строки, пары `Speaker`/`Text` из JSON-блобов,
  `ColorParserList`, `Settings.*` + подписи;
- перечисление печатных строк файла (кандидаты в `global_strings`) с дедупом по тексту;
- куча `#US` .NET-сборки (сам поиск кучи и её байты);
- blob'ы type tree и сырые байты типизированных объектов (base64) — как данные.

TS оставляет всю семантику и каталог:

- чтение type tree и generic-разбор объекта (`strings`/`fields`/`fsm_strings`,
  правила `SKIP_ATTRS`, PlayMaker `line_X`, FSM-обход);
- «это UI-текст?» (`isGlobalStringCandidate`, `uiPriority`, `isUiString`),
  синтез подписей настроек, отбор UI-строк из кучи `#US`;
- что вообще попадает в итоговый JSONL/POT, ключи и их порядок, дедуп, порядок
  ассетов, `summaries.jsonl`, `index.md`;
- POT/PO и всё ниже по течению.

**Почему не «весь дампер на Rust».** Правила извлечения (какие поля брать, что
считать текстом, как дедупить и сортировать) живут в одном месте — в TS. Второй
экземпляр этих правил в Rust означал бы: каждое изменение делать дважды и ловить
расхождения «почти совпало». Задача портфолийная, но код остаётся рабочим
инструментом, поэтому граница проведена по проверяемому признаку: Rust отдаёт
факты, TS решает.

**Цена границы.** Промежуточный rd1 — 523 МБ: из них ~134 МБ это base64 от 100 МБ
сырых байтов типизированных объектов (+33 % к их объёму), остальное — печатные строки
файлов и сканы объектов. Это лишний проход по диску; в бенчмарке он виден отдельной
строкой «сериализация» (6.2 с у TS, 1.6 с у Rust).

> Граница сдвинулась 2026-11-24: сборка дампа переехала в Rust, второй реализации
> семантики больше нет, TS удалён — см. §14.

## 3. Как воспроизвести (актуально после 2026-11-24)

Сравнительный стенд двух реализаций удалён вместе с TS; текущая проверка —
Rust против замороженного золота:

```bash
# 1. бинари (один раз)
npm run rust:build      # rust-decoder
npm run l10n:build      # rust-l10n (сборка дампа, potgen, po_update, po2dat)

# 2. золото сборки дампа (вход — git-фикстура, игра не нужна)
npm run test:assemble

# 3. полный дамп и полная сверка золота (нужен полный rd1 от реальной игры)
npm run dump -- --all --out tmp/dump
TCNN_FULL_GOLDEN=1 node --test scripts/assemble_parity.test.mts

# 4. золото POT/PO/QA
npm test                # includes scripts/text_parity.test.mts
npm run test:qa
```

Путь к игре — через `TCNN_GAME_DIR` (см. `scripts/game_dir.mts`), в папку игры
ничего не пишется. Тесты Rust с файлами игры гейтятся установкой: `cargo test --release --test game`
(без игры — печатает причину и выходит; в debug-сборке тест пропускается, потому что
полный прогон 2.18 ГБ там идёт ~5 минут).

## 4. Методика замера

- Один и тот же набор: `discoverGameFiles` (163 файла), порядок один и тот же.
- Каждый вариант запускается **отдельным процессом** — иначе `maxRSS` суммируется
  по всем замерам и цифры бесполезны.
- Время: wall time процесса варианта (`performance.now()` вокруг работы).
- Память: пиковая RSS. Для процесса Node — `process.resourceUsage().maxRSS`; для
  Rust — `PeakWorkingSetSize` из `K32GetProcessMemoryInfo` (бинарник пишет отчёт
  `--report`). В таблице — максимум по процессам варианта (они работают
  последовательно, поэтому пик пайплайна = максимум).
- Выход: размер каталога дампа (86.6 МБ) или файла rd1 (523 МБ).
- Два прогона: первый — «холодный» (файловый кэш ОС прогрет частично), второй —
  прогретый. Приводятся оба; выводы — по второму (устойчивому).
- Паритет внутри бенчмарка: rd1 от TS и Rust сравнивается побайтово, каталоги
  дампа — побайтово. Расхождение = провал прогона (код 1), а не «допустимая разница».
- Машина: Ryzen 7 7800X3D, 32 ГБ RAM, Windows 11, диск NVMe; Node 24.20, Rust 1.100
  (release, `lto=true`, `codegen-units=1`).

## 5. Байтовый уровень: TS-ядро против Rust-ядра

Обе стороны делают одну работу и пишут ОДИН файл rd1 (523 МБ), который потом
сверяется побайтово. Поэтому разница в этой таблице — чистая разница языков и
реализаций, без «TS делает больше».

| Вариант            | Прогон 1 | Прогон 2 | Пик RSS (пр. 1 / 2) | Выход    |
| ------------------ | -------- | -------- | ------------------- | -------- |
| `ts-core` (TS)     | 145.6 с  | 145.2 с  | 1306 МБ / 1314 МБ   | 499.3 МБ |
| `rust-core` (Rust) | 47.3 с   | 48.0 с   | 483 МБ / 483 МБ     | 499.3 МБ |

Фазы второго прогона (секунды; «сериализация» — запись rd1 в JSONL):

| Фаза                   | `ts-core`   | `rust-core` | Отношение |
| ---------------------- | ----------- | ----------- | --------- |
| чтение файлов          | 0.7 с       | 0.4 с       | 1.8×      |
| декомпрессия + таблицы | 8.1 с       | 3.2 с       | 2.5×      |
| сканы объектов         | 7.7 с       | 1.6 с       | 4.9×      |
| печатные строки файла  | 122.5 с     | 41.2 с      | 3.0×      |
| сериализация rd1       | 6.2 с       | 1.6 с       | 4.0×      |
| **итого**              | **145.2 с** | **48.0 с**  | **3.0×**  |

Что видно:

- **Печатные строки файла** (`runs`) — главный участок: TS материализует строку
  на каждый из 437 млн прогонов печатных байтов (2.18 ГБ входа, 736 млн символов),
  Rust делает то же самое, но аллокация + хэш-проверка дешевле вызова `TextDecoder`
  и создания JS-строки. Отсюда трёхкратный разрыв.
- **Декомпрессия и таблицы** (`decode`): 2.18 ГБ LZ4-блоков + 507 415 записей
  object table. Алгоритм в обеих реализациях свой и одинаковый по логике.
- **Сканы объектов** (`scan`): 507 415 объектов, поиск маркеров JSON-диалогов и
  печатных строк в сырых байтах — здесь Rust быстрее в 5 раз, но участок сам по
  себе маленький.
- **Сериализация** rd1 (523 МБ, компактный JSON + base64): свой писатель в Rust без
  промежуточных объектов против `JSON.stringify`/конкатенации строк в TS.
- **Память**: TS-ядро держит на файл `Set` из миллионов строк (до 2.8 млн в
  `resources.resource`) и поднимается до ~1.2–1.3 ГБ; Rust обходится 483 МБ.

## 6. Полный пайплайн (исторический замер): доля сборки

| Вариант                   | Прогон 1 | Прогон 2 | Пик RSS (пр. 1 / 2) | Выход   |
| ------------------------- | -------- | -------- | ------------------- | ------- |
| `ts` (полный TS-дампер)   | 119.3 с  | 122.9 с  | 1044 МБ / 1040 МБ   | 86.6 МБ |
| `rust` (ядро + TS-сборка) | 57.5 с   | 59.6 с   | 847 МБ / 846 МБ     | 86.6 МБ |
| в т.ч. ядро (Rust)        | 46.3 с   | 47.9 с   | 483 МБ              | —       |
| в т.ч. сборка (TS)        | 11.2 с   | 11.6 с   | —                   | 86.6 МБ |

`rust` = ядро (те же 46–48 с) + сборка дампа из rd1 (11.2–11.6 с). Сборка — это как раз
TS-семантика: чтение type tree, `strings`/`fields`/`fsm_strings`, фильтры UI-текста,
дедуп, порядок и запись 86.6 МБ итогового JSONL. В Rust её нет и не должно быть.

## 7. Где Rust выиграл и где TS догнал

Rust выиграл там, где работа действительно байтовая:

- **в 3.0 раза** на всём байтовом уровне (48.0 с против 145.2 с, включая запись
  того же 523-мегабайтного промежуточного файла);
- **в 3.0 раза** на печатных строках файлов — самом дорогом участке (41.2 с
  против 122.5 с);
- **в 2.5 раза** на декомпрессии UnityFS + разборе SerializedFile (3.2 с против
  8.1 с);
- **в 4.9 раза** на сканах 507 415 объектов (1.6 с против 7.7 с);
- **в 2.7 раза** по пиковой памяти (483 МБ против 1.3 ГБ).

TS догнал/остаётся незаменимым там, где начинаются правила:

- **сборка итогового дампа — 11.2–11.6 с**, и это ровно те правила, которые нельзя
  продублировать в Rust без нарушения DRY; на них приходится ~20 % полного
  времени пайплайна;
- **полный пайплайн — 57.5–59.6 с против 119.3–122.9 с (≈2.1×)**: после границы
  выигрыш «съедается» семантикой, и это честная цифра, а не 3×;
- **цена границы**: промежуточный rd1 — 523 МБ против 86.6 МБ итогового дампа
  (+33 % к типизированным байтам из-за base64). На маленьких наборах (3 файла,
  5 МБ) выигрыш меньше (1.8 с → 0.6 с): фиксированные издержки процесса и
  обмена начинают быть заметными.

### Профит в процентах (правило проекта: «считаем %, порог 10 %»)

Абсолютные секунды зависят от корпуса, поэтому то же самое в относительных числах.
Вход — 2.18 ГБ (2179.9 МБ) за один прогон:

| Метрика                      | `ts-core` | `rust-core` | Δ           |
| ---------------------------- | --------- | ----------- | ----------- |
| пропускная способность       | 15.0 МБ/с | 45.4 МБ/с   | **+202 %**  |
| время на корпусе             | 145.2 с   | 48.0 с      | **−66.9 %** |
| пиковая память               | 1306 МБ   | 483 МБ      | **−63.0 %** |
| полный пайплайн (пропускная) | 17.7 МБ/с | 36.6 МБ/с   | **+106 %**  |
| полный пайплайн (время)      | 122.9 с   | 59.6 с      | **−51.5 %** |
| полный пайплайн (память)     | 1044 МБ   | 847 МБ      | **−18.9 %** |

Оба варианта линейны по байтам (один проход, без квадратичных структур), поэтому
оценка на будущий объём — простое масштабирование: **корпус ×10 (21.8 ГБ)** даёт
`ts-core` ≈ 24.2 мин против `rust-core` ≈ 8.0 мин (экономия ≈ 16 мин за прогон), а
полный пайплайн — ≈ 20.5 мин против ≈ 9.9 мин (≈ 10.6 мин). Цена переноса при этом
платится один раз, а выигрыш — на каждом прогоне и на каждом новом языке/патче игры.

Порог «≥ 10 %» превышен двадцатикратно на байтовом уровне и десятикратно на полном
пайплайне — по правилу этого достаточно, чтобы **предложить** смену технологии. Но
предложение здесь сознательно узкое: переносится только байтовый уровень, потому что
перенос семантики (19.3 % времени пайплайна) стоил бы дублирования правил, а это
против DRY. Решение о полном переезде не принималось — оставлен рабочий переключатель.

## 8. Паритет: это не «почти совпало»

> **Область замера.** Числа ниже сняты на датасете **163 файла / 19 сцен = 0..15**
> (до расширения discovery до 19 сцен). После расширения — 169 файлов, POT 40 256 записей
> (2026-11-22). Пропорции от этого не меняются: обе реализации линейны по байтам, а паритет
> перепроверяется текущими тестами на актуальном наборе.

- **rd1 побайтово равны**: 523 571 473 байта — TS-ядро и Rust выдали идентичный
  файл на всех 163 файлах игры (сравнение каталогами и `cmp`).
- **Итоговый дамп побайтово равен**: 143 файла (`summaries.jsonl` + 142
  `<asset>.jsonl`) — сравнение каталогов в самом бенчмарке.
- **POT из двух дампов одинаковый** (после нормализации `POT-Creation-Date`):
  37 663 записи, 2 193 341 байт, `sha256` = `17e61281…a238b4`; `dump_parity --jsonl` —
  142 файла / 507 578 строк / 0 расхождений. Проверено и через CLI
  (`dump --decoder rust` на всю игру: 163 ассета, 507 415 объектов).
- **В тестах**: `rust_parity.test.mts` проверяет оба уровня на синтетических
  фикстурах (файлов игры в git нет) и пропускается, если бинарь не собран;
  `cargo test` держит байтовый уровень со своей стороны (37 юнит-тестов +
  интеграционные), `cargo test --release --test game` — прогон по установленной
  игре (в debug пропускается: 2.18 ГБ дают ~5 минут).

## 9. Условия пересмотра границы

1. **Доля семантики вырастет** (новые правила POT/фильтров) — не тянуть её в Rust
   по частям: переносить правило вместе с тестами и удалять TS-копию, иначе
   появится второй источник истины.
2. **Дамп станет инкрементальным** (дельта-файлы вместо полного прогона) —
   промежуточный обмен перестанет быть доминантой, выигрыш Rust вырастет.
3. **Появится параллельный/потоковый декод** — Rust выиграет сильнее (треды без
   GIL), TS-путь останется однопоточным.
4. **CI без rustup или кроссплатформенность в приоритете** — раньше это был аргумент
   оставить TS-путь; после 2026-11-24 второго пути нет, поэтому Rust-джоб стал
   обязательным (`rust-toolchain.toml` пинит тулчейн).

## 10. Ограничения честности замера

- Время — wall time процесса; RSS — пик рабочего набора (для Rust —
  `PeakWorkingSetSize` из `K32GetProcessMemoryInfo`, для Node —
  `process.resourceUsage().maxRSS`).
- `ts-core` — не продакшн-путь, а эталон формата: он делает ту же работу, что Rust,
  включая запись 523 МБ. Поэтому его время (145.2 с) больше времени полного
  TS-дампа (122.9 с) — ровно на цену промежуточного формата (base64 + 523 МБ записи
  - `Set` печатных строк), которой у полного TS-дампа нет.
- Числа на этой машине (Ryzen 7 7800X3D, 32 ГБ, NVMe, Windows 11, Node 24.20,
  Rust 1.100 release). Воспроизведение — одной командой, см. §3.

## 11. Что добавить в npm (историческая заявка; сейчас уже в `package.json`)

```json
"rust:build": "cargo build --release --manifest-path tools/rust-decoder/Cargo.toml",
"rust:test": "cargo test --manifest-path tools/rust-decoder/Cargo.toml",
"dump:rust": "node .opencode/skills/dump-assets/scripts/dump_assets.mts dump --decoder rust"
```

Стенд `bench:dump` (`scripts/dump_bench.mts`) удалён 2026-11-24 вместе с TS-реализациями:
сравнивать больше не с чем, а время Rust пишется в отчёт самого дампа.

Джоб CI (исходный шаблон; актуальный — в `.github/workflows/ci.yml`, там же золотые
гейты и сборка `rust-l10n`):

```yaml
rust:
  runs-on: ubuntu-latest
  defaults:
    run:
      working-directory: tools/rust-decoder
  steps:
    - uses: actions/checkout@v4
    - uses: dtolnay/rust-toolchain@master
      with:
        toolchain: "1.100.0"
        components: rustfmt, clippy
    - uses: Swatinem/rust-cache@v2
      with:
        workspaces: tools/rust-decoder
    - run: cargo fmt --check
    - run: cargo clippy --all-targets -- -D warnings
    - run: cargo test
```

## 12. Решение (2026-11-22)

Владелец: «скорость работы с данными важна; ускорение даже на 10 % на большом отрезке даёт
результат». По критериям из `docs/language-audit.md` (профит измерен, ресурсы лучше) принято:

- **Рабочий декодер — Rust** (`npm run dump`): байтовый уровень 3.0× быстрее и 2.7× экономнее
  по памяти, весь пайплайн 2.1× быстрее.
- **Оракул — золотые фикстуры**: `test_data/assemble-golden-*` (сборка дампа),
  `pot-golden*` (POT), `po-update-golden/` (перенос переводов), `qa-golden-<lang>.json`
  (QA). Сняты с TS ДО его удаления (2026-11-24) и лежат в git; тесты сверяют Rust →
  слепок побайтово.
- **Условия пересмотра:** если Rust перестанет давать ≥2× (при появлении нового
  кандидата) или появятся проблемы со сборкой/портативностью — возвращаемся на TS
  по тому же правилу.

Удаление Python-дампера выполнено в этот же день: он больше не нужен ни как источник, ни как
оракул — паритет зафиксирован числами, а оракулом стала пара TS↔Rust. **2026-11-24 TS-сторона
тоже удалена**: числа зафиксированы, роль оракула перешла к золотым фикстурам, второй
реализации больше нет.

## 13. Правило удаления аналога (владелец, 2026-11-23)

Решение: **как только реализация на Rust доказана и протестирована — старый аналог удаляется в
том же коммите.** Два рабочих экземпляра = гарантированный дрейф и двойная работа на каждую
правку; дубли в репозитории не живут.

Граница, которая делает удаление безопасным: **оракул замораживается в файлы до удаления.**

- побайтовый паритет на реальном корпусе и фикстурах — уже есть (см. раздел 3);
- фикстуры и `sha256`/байтовые слепки выхода коммитятся **до** удаления кода;
- тест сравнивает Rust → слепок (`scripts/text_golden.test.mts`), а не Rust → TS;
- любое изменение выхода падает тестом и требует осознанного обновления слепка
  (`GOLDEN_UPDATE=1 npm run test:golden`), которое видно в диффе.

### Статус миграции

| модуль                 | рабочая реализация | прежний TS-эталон | состояние                                           |
| ---------------------- | ------------------ | ----------------- | --------------------------------------------------- |
| dumper (байтовый слой) | Rust               | `dump:ts`         | **удалён 2026-11-24**, оракул — `assemble-golden-*` |
| сборка дампа           | Rust               | `--assembler ts`  | **удалён 2026-11-24**, золото сборки                |
| `potgen`               | Rust               | `potgen:ts`       | **удалён 2026-11-24**, `pot-golden*`                |
| `po_update`            | Rust               | `po:update:ts`    | **удалён 2026-11-24**, `po-update-golden/`          |
| `po2dat`               | Rust               | —                 | **удалён 2026-11-23**, слепок `.dat`                |
| `prefill`              | Rust               | —                 | **удалён 2026-11-23**, слепок `.po`                 |
| `find_source`          | Rust               | —                 | **удалён 2026-11-23**, слепок вывода                |
| QA-ядро                | Rust               | `qa:ts`           | **удалён 2026-11-24**, `qa-golden-<lang>.json`      |

### Что удаление требует проверить

1. Потребители переключены: `package.json`, скиллы, деплой, чекер.
2. Тесты удалённого модуля **портированы** в Rust 1:1 (не «примерно покрыто»), иначе удаление
   теряет кейсы: так было с `po2dat`/`prefill` (11 и 21 кейс переехали как есть).
3. Слепок выхода лежит в git и тест на него зелёный.
4. Удаление и переключение потребителей — в одном коммите (иначе репозиторий в промежутке
   собирается непонятно чем).

## 14. Сборка дампа в Rust; TS-реализации удалены (2026-11-24)

Граница, описанная в разделе 2 («байты в Rust, семантика в TS»), сдвинулась
осознанно: владелец попросил максимум профита как задел для масштабирования.
Сначала вторая реализация семантики осталась как ОРАКУЛ, а не рабочий путь
(та же схема, что у `potgen`/`po_update`); затем, после доказанного паритета,
TS-реализации были удалены целиком.

Новый рабочий путь: `dump_assets dump --decoder rust` → `rust-l10n dump_assemble`
(ассемблер в Rust). Флаг `--assembler ts` **не работает**: он завершается
ошибкой с объяснением (2026-11-24, коммит `7f170cb`).

**Что изменилось 2026-11-24.** Удалены TS-декодер и TS-сборка дампа, QA-ядро
(`qa_translate.mts`), `potgen.mts` и `po_update.mts`; вместе с ними ушли команды
`dump:ts`, `qa:ts`, `potgen:ts`, `po:update:ts` и сравнительные стенды
`dump_parity`/`dump_bench`. Рабочая реализация всех стадий — Rust, а **оракул —
золотые фикстуры**: побайтовые слепки выхода, снятые с TS до удаления и
закоммиченные в `test_data/` (`assemble-golden-small/`, `assemble-golden-full.json`,
`pot-golden*`, `po-update-golden/`, `qa-golden-<lang>.json`). Гейты:
`scripts/assemble_parity.test.mts`, `scripts/text_parity.test.mts`,
`translate-qa/tests/qa_golden.test.mts`.

Замер на полном корпусе (169 ассетов, 578 474 объекта, rd1 530 МБ, выход 134 МБ):

- сборка: **6,5 с** (Rust) против **11,6 с** (TS-эталон) — **1,8×**;
- полный дамп: **60,1 с → 53,6 с** (декодер 48 с + сборка), без изменения формата;
- паритет: **149 из 149 файлов** побайтово (`summaries.jsonl`, `<asset>.jsonl`,
  `index.md`), включая плавающие (`repr`), порядок ключей и обрезки.

Что оказалось неочевидным (и почему паритет — не формальность):

- **Плавающие.** `format!("{}", f64)` и Python `repr` расходятся на ничьих:
  `0.6244583129882812` у эталона против `…13` у Rust (Rust округляет вверх,
  dtoa — к чётной цифре). Решение: искать минимальную точность, при которой
  `{:.*e}` читается обратно в тот же `f64`; форматирование Rust округляет
  корректно (half-to-even).
- **Форматы полей.** `settings_keys` — массив `[{key, display}]`, а
  `color_parser_list` — объект `{имя: hex}`; перепутать легко, паритет ловит.
- **`path_id`** печатается без кавычек как 64-битное целое (в rd1 он строкой).

Профиль стоимости сборки: разбор rd1 — 3,2 с (последовательный, 167 МБ/с),
сборка+запись — 3,3 с. Дальнейший шаг — параллельная сборка по ассетам
(задача `tasks/2026-11-24-rust-assemble.md`), ожидаемо ~4 с суммарно.
