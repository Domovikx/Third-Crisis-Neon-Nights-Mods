# Потери текста в дампере: что резалось, что убрано и чем это грозит POT

Дата: 2026-11-22. Задача: убрать молчаливые обрезки в `dump-assets` (источник данных),
не трогая `po/`. Аудит, который это выявил — `docs/pot-coverage-audit.md`.

Режим: `po/` только читался; POT собирался в `tmp/` (`tmp/pot-from-before.pot`,
`tmp/pot-from-after.pot`), `po/template.pot` не перезаписан.

> Обновление 2026-11-24: TS-реализации дампера и сборки удалены; те же правила и
> лимиты живут в Rust (`tools/rust-decoder`, `tools/rust-l10n/src/assemble.rs`).
> Имена `.mts`/`.py` в тексте — исторические, команды `--decoder ts` больше нет.

## 1. Короткий ответ

Дампер терял текст в пяти местах, и делал это **молча**. Три обрезки сняты полностью
(без лимита), одна осталась как осознанная защита от мусора, одна — как паритет с
Python-эталоном; все оставшиеся **считаются и печатаются** в конце прогона.

| Что резалось              | Было               | Стало                             | Что это дало                       |
| ------------------------- | ------------------ | --------------------------------- | ---------------------------------- |
| `raw_strings` на объект   | `[:100]`, тихо     | без лимита (`--raw-string-limit`) | +2 940 429 строк у 1 768 объектов  |
| UI-строки из кучи `#US`   | `[:500]`, тихо     | без лимита (`--dotnet-ui-limit`)  | +251 строка `settings_keys`        |
| `fsm_strings` на объект   | `[:500]`           | без лимита                        | не достижим (макс. 11 на объекте)  |
| `global_strings` на ассет | `[:500]`, тихо     | 500 + счётчик обрезки             | 0 (поле в POT не читается)         |
| значение строкового поля  | 500 символов, тихо | 500 + счётчик обрезки             | 1 значение (lorem ipsum в префабе) |

Цена: дамп 95 → 134 МБ (+41 %), время прогона 63.5 → 64.1 с (шум).
POT из нового дампа: 40 256 → 143 871 записей (+103 615), **из них прозы только ~3 тыс., а
100 688 — мусор бинарного скана**. Это не ошибка дампера: он больше ничего не теряет, но
фильтр `isUiString` в инвентаре (`extract-text`, не зона этой задачи) пропускает мусор.
**Правило: `po/template.pot` не перегенерировать, пока фильтр не ужесточён** (раздел 4).

## 2. Точки потерь и что с ними сделано

- **`extract.mts` — `raw_strings[:100]`.** Снято: по умолчанию отдаются все строки объекта
  (`null` = без лимита). Мотив — на корпусе обрезка отбрасывала 70.7 % всех raw-строк
  (40.6 МБ текста) у 1 768 объектов, и хвост не доходил ДО фильтров; в хвосте 3 288
  маркеров `line_` (признак PlayMaker-диалогов) — то есть терялись и реплики.
- **`dotnet.mts` — `.slice(0, 500)` после сортировки по приоритету.** Снято: из кучи `#US`
  берутся все UI-кандидаты (751 на корпусе вместо 500). Сортировка по приоритету осталась —
  она задаёт порядок, а не состав.
- **`dump_assets.mts` / `rawscan.mts` — `global_strings[:500]` на ассет.** Лимит оставлен
  (500 — значение по умолчанию), потому что это поле **никто не читает** (ни инвентарь, ни
  POT), а кандидатов без лимита 2 061 610 против 75 795 попадающих в дамп: это мусор
  бинарного скана. Теперь обрезка считается и печатается; лимит поднимается флагом
  `--global-string-limit` (или снимается `all`).
- **`extract.mts` — `parseFsmStrings` останавливался на 500 строках.** Снято. На корпусе
  максимум — 11 строк на объект, то есть лимит не срабатывал, но был тихой миной.
- **`MAX_STRING_LEN = 500` на одно значение** (типизированные строки, `raw_strings`,
  `dialogues.text`). Значение оставлено: это контракт с Python-эталоном и Rust-сканером
  (`MAX_STRING_LEN` в `tools/rust-decoder/src/rawscan.rs`), менять его — отдельное решение
  с пересборкой корпуса. Вместо тишины — счётчик по типизированным строкам: на корпусе он
  показывает **1 значение** (префаб релиз-нот, `m_text` с lorem ipsum). Для `raw_strings`
  срез происходит ещё на байтовом уровне (общий с Rust), поэтому в отчёт не попадает, но
  замер сделан: 1 056 строк упираются в 500 символов, и **все они — склейки путей спрайтов**
  (`bodysuit_outfit_cat01&ZoeyOutfitCat01/...`), а не текст. Самый длинный диалог в корпусе —
  209 символов, то есть реплики не режутся.

Отчёт о любой обрезке печатается в stderr в конце прогона, даже если обрезано 1 значение:

```text
ВНИМАНИЕ: при извлечении отброшены строки (это не тихо):
  global_strings: отброшено 1986510 (затронуто: 137, лимит: 500)
  значения строк длиннее MAX_STRING_LEN: отброшено 1 (затронуто: 1, лимит: нет)
```

Пределы прогона печатаются и в начале (`пределы: raw_strings=без лимита/объект,
global_strings=500/ассет, #US=без лимита/сборка`), поэтому журнал запуска самодостаточен.

## 3. Замер «до/после»

Один и тот же корпус (169 ассетов игры, `--decoder rust`), один и тот же диск.
«До» — код до правки (`tmp/dump-before`), «после» — после (`tmp/dump-after`).

| Показатель                 | До            | После         | Δ              |
| -------------------------- | ------------- | ------------- | -------------- |
| Время полного дампа        | 63.5 с        | 64.1 с        | +0.6 с (шум)   |
| Размер каталога дампа      | 95 МБ         | 134 МБ        | +39 МБ (+41 %) |
| Ассетов / объектов         | 169 / 578 474 | 169 / 578 474 | 0              |
| Объектов с новыми строками | —             | 1 768         | +1 768         |
| Новых строк `raw_strings`  | —             | 2 940 429     | —              |
| `settings_keys` (обе DLL)  | 747           | 998           | +251           |
| `global_strings`           | 75 795        | 75 795        | 0              |

Промежуточный `rd1` не изменился (530 МБ): байтовый уровень и раньше отдавал все строки,
резала их семантика на TS. Поэтому Rust-правок не потребовалось — паритет только проверен
(раздел 5). Для справки: TS-путь того же дампа идёт 2 мин 26 с и даёт побайтово тот же
каталог (он дороже на байтовом уровне, см. `docs/rust-vs-ts.md`).

Распределение новых строк по ассетам (топ): `resources` +984 966 у 422 объектов,
`sharedassets0` +304 626 у 57, дальше — крупные CG/анимационные бандлы по 120–145 тыс.
Ни один объект не «появился из пустоты»: у всех 1 768 уже было ≥100 строк, то есть терялся
именно хвост.

## 4. Что это даёт POT (POT собирался в `tmp/`, `po/` не тронут)

```bash
node scripts/text_cli.mts potgen --dump tmp/dump-before --out tmp/pot-from-before.pot  # 40 256
node scripts/text_cli.mts potgen --dump tmp/dump-after  --out tmp/pot-from-after.pot   # 143 871
```

- POT из «до» = **40 256** записей — совпадает с текущим `po/template.pot` (различие только
  в `POT-Creation-Date`), базовая линия воспроизводится.
- POT из «после» = **143 871** → **+103 615 записей**.
- Из добавленных: **147** похожи на предложения (≥3 слов и точка в конце), **2 927**
  проходят мягкий фильтр «похоже на текст» (включая эти 147), остальные **100 688** — мусор
  бинарного скана (случайные последовательности вроде `! #.9EQ]gu`,
  `"printer_core_progress_lights copy`).
- Ещё **23 960** добавленных — сырые оболочки строк, которые в POT уже есть (числовой
  префикс, rich-теги, хвостовой номер). После нормализации это дубликаты, а не новый текст.

Примеры настоящего текста, который раньше не доходил (хвост `raw_strings` сцен и бандлов):

- `[10] Lay your hand on his cock.`, `[400] Pay the half price.`
- `Did Klaudia walk to Cal?`, `Are we on mission to get upstairs?`
- `Is Use Blocker in progress?`, `Did backroom Scolding?`

Примеры из кучи `#US` (+251 строка `settings_keys`), которые раньше отрезал top-500:
`Overwrite Save`, `Lovense Toy Search`, `APP NOT FOUND`, `New Version Available!`,
`Achievement Unlocked!`, `The entire Gallery has now been unlocked!`,
`Simplified Chinese Machine Translated / 中文机器翻译`.

**Вывод для пайплайна.** Дамп больше не теряет текст, но POT из него собирать рано:
`isUiString` в `inventory.mts` (зона `extract-text`) пускает в POT всё, что похоже на
«многословный лейбл», включая обрывки бинарных блобов. Пока фильтр не ужесточён (и пока не
решено, что из `raw_strings` вообще переводимо), `po/template.pot` перегенерировать нельзя.
Точные кандидаты на починку фильтра перечислены в `docs/pot-coverage-audit.md` (раздел про
`isUiString`); это отдельная задача, здесь она намеренно не трогалась.

## 5. Паритет с прежним путём (история)

Обрезки применялись в общей семантике (`extract.mts`, `dotnet.mts`, `rawscan.mts`,
`dump_assets.mts`); TS-путь и его тесты удалены 2026-11-24, правила перенесены в Rust
1:1. Проверено было:

- `tests/rust_parity.test.mts` — фикстура дополнена объектом со 150 raw-строками:
  без лимита в дампе все 150 (в обоих путях), с `rawStringLimit: 100` оба пути дают
  побайтово одинаковый JSONL и одинаковый отчёт обрезки (`units: 1, dropped: 50`);
- полный реальный прогон: `--decoder ts` (`tmp/dump-after-ts`, 2 мин 26 с) против
  `--decoder rust` (`tmp/dump-after`, 64 с) — `diff -r -q` вернул 0 расхождений:
  148 JSONL-файлов (147 ассетов + summaries), 578 474 объекта, оба отчёта об обрезке
  совпали символ в символ.

## 6. Типизированные UI-поля (`m_text`, `Description`, `UnlockHint`, …)

Исследовано, чинить не стали — и вот почему это не потеря дампера.

- **В `.assets` (`level*`, `sharedassets*`, `resources`) поля недоступны в принципе.**
  Type tree там выключен (`typeTree=false` во всех файлах этих трёх видов — факт из
  `MAP.md`), объекты
  MonoBehaviour читаются как `read_failed`. Байтовый скан «по известным именам полей» не
  спасёт: **имён полей в байтах объектов нет**, есть только значения. Проверено поиском по
  бинарю игры: `m_text` в `level2` и `sharedassets2.assets` — 0 вхождений; в
  `resources.assets` 11 вхождений, но все — подстроки других имён (`allocated_ram_text`,
  `ram_text_inside_graph`, `mono_ram_text`). Python-эталон на `.assets` тоже даёт
  `read_failed`, то есть это не регресс TS.
- **В бандлах поля извлекаются и уже лежат в дампе.** Type tree есть, `strings` заполняется:
  `Description` 83 значения, `UseText`/`TakenFromInventoryText` по 90, `DisplayName` 76,
  `m_text` 49, `DefaultDisplayName` 9, `UnlockHint` 6. Из них нет в `po/template.pot`:
  `DefaultDisplayName` 9/9, `UnlockHint` 5/6, `Description` 11/83, `m_text` 7/49,
  `DisplayName` 2/76 — итого ~35 значений, из них прозы ~28.

  Примеры (всё это видит игрок, в POT нет):
  `Just an old pair of shorts to wear around my apartment.` (`Description`),
  `Get the power back on.` (`DefaultDisplayName`, шаг квеста),
  `Visit the bathroom in room 205 during Zoey's dream sequence.` (`UnlockHint` галереи),
  `Zoey's Rutter encounter.` (`DisplayName`).

- **Значит потеря typed UI — не в дампере, а в инвентаре**: `inventory.mts` берёт из
  `strings` только `m_Name` (нужен для логики бандлов), а UI-поля игнорирует. Починка =
  правила отбора полей в `extract-text` (там же и фильтр), это отдельная задача. Резать
  дампер здесь нечего: данные уже есть.

Схему «вслепую» не выдумывали: у `.assets` нет type tree, а без имён полей эвристика
«после известного имени прочитать длину и строку» работать не может — поле неотличимо от
бинарного шума. Единственный честный путь для `.assets` — база type tree по типу скрипта
(как у UnityPy для встроенных классов), это большая отдельная работа, и она не нужна, пока
POT не использует даже те typed-поля, что уже есть в дампе.

## 7. Что осталось

- **Фильтр `isUiString` и отбор `strings.*`** (`extract-text`) — следующий шаг: без него
  POT нельзя перегенерировать (раздел 4).
- **`global_strings`** — поле остаётся за лимитом 500 и не читается никем; если понадобится,
  лимит поднимается флагом, но сначала нужен потребитель и фильтр.
- **`MAX_STRING_LEN = 500`** — оставлен ради паритета с Python-эталоном и Rust; теперь
  считается. Менять — только вместе с `rawscan.rs` и пересборкой корпуса.
- **`.assets` typed UI** — только через базу type tree (раздел 6).

## 8. Как воспроизвести

```bash
# 1. дамп (по умолчанию все строки: raw_strings без лимита, #US без лимита)
node .opencode/skills/dump-assets/scripts/dump_assets.mts dump --decoder rust --out tmp/dump-after

# 2. дамп с явными лимитами (обрежется — напечатает счётчик)
node .opencode/skills/dump-assets/scripts/dump_assets.mts dump --decoder rust \
  --raw-string-limit 100 --global-string-limit 500 --dotnet-ui-limit 500 --out tmp/dump-limited

# 3. POT в tmp (в po/ ничего не пишется)
node scripts/text_cli.mts potgen --dump tmp/dump-after --out tmp/pot-from-after.pot

# 4. тесты и паритет
npm run test:dump
```
