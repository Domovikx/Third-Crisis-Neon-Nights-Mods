# Аудит конвейера: игра → дамп → POT → PO → игра

Дата: 2026-11-23. Метод: чтение кода каждой стадии + замеры на реальных данных
(дамп 578 474 объекта, POT 18 366, `ru.po` 15 284) + прогоны и тесты. Всё, что
ниже, проверено на файлах; где проверка возможна только в игре — это помечено.

## 1. Карта и контракты

| стадия    | вход                                      | выход                          | владелец кода                         |
| --------- | ----------------------------------------- | ------------------------------ | ------------------------------------- |
| дамп      | `*.assets`, бандлы, `Assembly-CSharp.dll` | `tmp/dump-after/*.jsonl`       | `dump-assets` (Rust-байты + TS-смысл) |
| инвентарь | JSONL                                     | `{text,speaker,rich,kind,src}` | `extract-text/inventory`              |
| каталог   | инвентарь                                 | `(msgid,msgctxt)→slot`         | `potgen`                              |
| отбор     | каталог + `config/pot-src-policy.json`    | POT без ассетов                | `potgen`                              |
| skip      | каталог + политика + `pot-skip-ids.json`  | `#, skip` в POT                | `potgen`                              |
| POT       | —                                         | `po/template.pot`              | `potgen` (Rust)                       |
| перевод   | POT + `po/<lang>.po` + дамп (контекст)    | `po/<lang>.po`                 | `translate-local`                     |
| словарь   | PO + `#. rich_text:` (POT)                | `runtime/patch_<lang>.dat`     | `po2dat` (Rust)                       |
| игра      | `.dat`                                    | заменённый текст TMP           | C# рантайм (`build-translator`)       |

Контракты зафиксированы тестами: POT — `docs/pot-contract.md` (14+ инвариантов),
PO — `references/PO_FORMAT.md`, rich — `docs/rich-text-audit.md`.

## 2. Дыры и риски

### P0 — чинить до следующего длинного прогона

**2.1. (решено 2026-11-23) Бэкенд умирает на длинных прогонах.** За сессию три падения
`HTTP 400 {"error":"terminated"}`: процесс инференса LM Studio завершается, модель
выгружается, прогон встаёт. В соседнем проекте (TSSR) это уже проходили и решили
переходом на **headless `llama-server`** из бэкендов LM Studio (`-c 8192 -np 4`,
порт 8081): «прогон стоял» у GUI-сервера, на headless — 1 132 строки без сбоев.
Дополнительно: llama.cpp не понимает `reasoning_effort`, thinking там гасится
`chat_template_kwargs: {enable_thinking: false}` — наш код отправляет только
первое, значит на llama-server «размышления» вернутся.
Сейчас смягчено ретраями и перезагрузкой модели, но это лечение симптома.

**Решение:** перешли на headless `llama-server` (порт 8081, `-c 8192 -np 1`,
`--alias index-translate-9b`). Проверено: сервер поднимается за секунды, `/health`
= ok, 14 строк разметки прошли без единого сбоя. Наш код теперь отправляет и
`reasoning_effort`, и `chat_template_kwargs: {enable_thinking: false}` — первое
понимает LM Studio, второе llama.cpp.

**2.2. У C# рантайма нет unit-тестов.** `.opencode/skills/build-translator/tests`
содержит только тест сборки. Логика, от которой зависит весь результат в игре —
приоритет `rich_translation > translation > rich_text > text`, вычисление
`plain = strip(rich)`, `Replace(plain, tr)`, поведение при inline-тегах — проверяется
лишь запуском игры. Ошибка в ней не ловится ни одним тестом.

### P1 — качество и покрытие

**2.3. Семантическое качество не проверяется автоматически.** Наши валидации
ловят форму (теги, маркеры, токены подстановки), но не смысл. Показательный
случай: **30 переводов начинались с «2. »** — утечка номера строки из нашего же
протокола `N. translation`; нашлось только ручным аудитом (исправлено, детектор
`numbering` добавлен). В TSSR для этого есть механическое ревью (11+ классов) и
судья LLM (flag-only, калибровка 61/64 при 0 ложных).

**2.4. Нет карты пола и канона имён.** Модель выводит адресата («ты пришёл/пришла»)
и написание имён из контекста, то есть угадывает. В TSSR пол берётся из
`casts/gender.mts`, а канон имён — из строк `msgctxt "speaker-name"`; промпт
подаёт их явно. У нас `speaker-name` в POT есть, но канон не подаётся, а карты
пола нет вовсе.

**2.5. Реплики нарезаны на куски, стыки не проверяются.** Игра хранит диалог
частями, иногда с середины слова: **443 живые строки начинаются не с начала фразы**
(`", falling back to English."`, `"s falling apart outside these walls…"`).
Перевод идёт по кускам (с контекстом 2+1), но итоговая склейка в игре не
сравнивается: каждый кусок может быть верным, а вместе — нет. Нужен ревью-вид
«склейка соседних кусков одного диалогового объекта», это данные у нас есть
(`source`/`idx` в инвентаре).

**2.6. Шаблоны с подстановкой не работают в рантайме.** `Received #ItemName#.`
рантайм ищет точным совпадением и никогда не увидит после подстановки. Сейчас
такие строки в skip (4 записи), но игрок видит их по-английски. Нужен матчинг по
шаблону (разбить на литералы и токены), иначе класс не закрыть.

**2.7. `global_strings` не читается инвентарём.** По аудиту покрытия — 57 539
кандидатов, 4 034 «прозы». Это не ошибка отбора, а непройденный путь: часть
текста может не попадать в POT вообще.

### P2 — аккуратность

**2.8. Наивная чистка тегов осталась в одном месте.** `inventory.stripRich`
(`<[^>]+>`) применяется к `bundle`-строкам; именно эта чистка породила обрывки в
`dialog`. Сейчас `self-fragment = 0`, но класс жив: авторские кавычки `< … >` в
бандле дадут тот же хвост. Лечение — тот же `stripTmpTags`, что в `pot_skip`.

**2.9. `rt` покрыт на 353 из 385 inline-строк `ru`.** 32 без `rt`: там теги
подсвечивают междометие (`Fffh`), а перевод его перефразирует — модель не может
найти соответствие. Это дефект переводов, а не разметки: нужен ревью этих 32.

**2.10. `de`/`pl` унаследованы без разметки.** 287 inline-строк на язык без `rt` —
при включении этих языков оформление пропадёт. Это долг, не потеря.

## 7. Ограничения этого аудита

- В игре проверялся только экран меню; диалоги с разметкой и `rt` в живом
  рантайме не подтверждены (сессия Windows была заблокирована).
- Поведение `UILocalization._originalText` для диалогов не проверено: неизвестно,
  приходит ли туда чистый текст или строка с тегами. От этого зависит, работает
  ли поиск по ключу для строк с разметкой.
- Оценка «сколько игрок не видит по-английски» не измерена: для этого нужен
  проход по игре или анализ всех мест, где TMP получает текст.

## 10. Шаблоны подстановки (2.6): что именно осталось

В POT **4** строки с подстановкой, все в `#, skip`:

- `#TakenFromInventoryText# #ItemName#.` и `Received #ItemName#.` — видимые игроку фразы;
- `Screen: ####x####@##Hz` и `Window: ####x####@##Hz[###dpi]` — форматы разрешения, переводить нечего.

Почему не чинится в PO: рантайм подставляет значение и ищет перевод по **итоговой** строке
(`Received Iron Dagger.`), а у нас в каталоге лежит шаблон — точного совпадения не будет никогда.

**Ответ найден в коде загрузчика** (`.opencode/skills/build-translator/source/TranslationLoader.cs`):
словарь строится как `_translations[text] = best` по английскому тексту, а `TranslatorPlugin`
проверяет `_translations.ContainsKey(orig)` — **только точное совпадение, без шаблонов и
префиксов**. Значит подставленная строка не совпадёт с шаблоном никогда, и это не вопрос
порядка подстановки: нужен матчинг по шаблону на стороне плагина.

Два возможных пути (оба — правка плагина, не PO):

1. если игра подставляет **уже переведённое** имя предмета — можно развернуть шаблон по списку
   предметов и положить в PO готовые строки (`Получен {переведённое имя}.`);
2. если подставляет английское имя — разворот бесполезен, нужен матчинг по шаблону на стороне
   загрузчика.

Проверяется только в живой игре (взять предмет и посмотреть строку). Пока — известное
ограничение на 2 фразы.
