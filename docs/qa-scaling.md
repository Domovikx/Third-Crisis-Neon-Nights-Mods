# QA перевода на Rust: замер масштабирования (проценты, не секунды)

Дата: 2026-11-22. Основание: `tasks/2026-11-22-rust-qa-spike.md`, правило
`AGENTS.md` «Языки» (профит только по замеру; порог предложения — прирост ≥ 10 %,
миграция ради скорости — ≥ 2× на реальной нагрузке).

## 1. Вопрос и короткий ответ

Вопрос: **стоит ли переносить QA перевода (`qa_translate`) на Rust**, если мерить не
секунды на текущем корпусе (7 МБ, ~0.3 с), а коэффициент на будущих объёмах (новелла
×10 и ×100)?

Ответ: **да, вычислительное ядро — стоит**. На всех трёх объёмах Rust быстрее в
**2.6–3.7 раза**, а на 100× TypeScript вообще не работает без поднятого heap
(падает по памяти на дефолтных ~4 ГБ), тогда как Rust завершает без флагов. HTML-отчёт
остаётся в TypeScript: рендер — не узкое место, дублировать разметку незачем.

## 2. Что сравнивается

Обе реализации решают одну задачу и выдают один отчёт: сводка (покрытие, errors,
warnings, по спикерам и папкам) + находки `(level, rule, rel, text, detail)`.

- **TS-эталон** — `.opencode/skills/translate-qa/scripts/qa_translate.mts` (не менялся).
  Написан на Node по `.mts`, включая старт процесса.
- **Rust** — `tools/rust-qa` (крейт `rust-qa`, бинарь `rust-qa`): свой PO-парсер,
  `serde_json` только для JSONL `.dat`, 6 правил, вывод JSON/JSONL.

Граница проведена так же, как у дампера (`docs/rust-vs-ts.md`): Rust делает работу с
данными и правилами, TS остаётся **эталоном-оракулом** и рисует HTML. Правила перенесены
1:1 (включая порог латиницы и фильтр `<font>`/`<material>`), а не переписаны «как лучше».

## 3. Как воспроизвести

```bash
# 1. бинарь (один раз)
cd tools/rust-qa && cargo build --release && cd ../..

# 2. паритет на текущих данных + замер 1× / 10× / 100× (2 прогона на точку)
node scripts/qa_scaling_bench.mts --scales 1,10,100 --runs 2

# точечно:
node scripts/qa_scaling_bench.mts --scales 1              # только паритет на реальных ru и de
node scripts/qa_scaling_bench.mts --scales 10 --regen     # перегенерировать синтетику 10×
```

Синтетика кладётся в `tmp/qa-bench/<n>x/` и в git не попадает. Результаты —
`tmp/qa-bench/results.json`.

## 4. Методика замера

- **Объёмы.** `1×` — настоящие файлы репозитория (`po/template.pot`, `po/ru.po`,
  `runtime/patch_ru.dat`). `10×` и `100×` — синтетика, сгенерированная тем же скриптом:
  каждая запись POT повторена N раз.
- **Уникальность записей.** К `msgid` дописывается не-буквенный хвост `~k` (доля
  кириллицы и «латиница» от него не меняются), к не-спикерским `msgctxt` — тоже `~k`,
  чтобы ключ `(msgctxt, msgid)` не мог схлопнуться. Хвост одинаково попадает и в POT,
  и в `.dat`, поэтому правила видят те же данные с обеих сторон.
- **Что повторяется.** Все 40 256 записей POT (не выборка), с сохранением флагов
  (`#, legacy` и пр.) и rich-полей `r`/`rt`; строки `.dat` генерируются только для тех
  текстов, у которых они есть в реальном `.dat` (покрытие и доля пустых диалогов
  сохраняются).
- **Прогоны.** Каждый инструмент запускается **отдельным процессом**; wall time
  измеряется вокруг `spawnSync`, то есть включает старт рантайма. Два прогона на точку:
  первый — холодный (кэш ФС), второй — прогретый. В таблице приводятся оба.
- **МБ/с** — входные байты (POT + PO + DAT) на время процесса, 1 МБ = 2^20 байт.
- **Heap для TS.** На 100× (4 млн записей) дефолтный лимит Node (~4 ГБ) не хватает —
  процесс падает с `FATAL ERROR: Ineffective mark-compacts near heap limit`. Это часть
  результата. Чтобы измерить время, бенчмарк запускает TS с
  `NODE_OPTIONS=--max-old-space-size=8192` (`--ts-heap-mb`); Rust таких флагов не требует.
- **Гейт паритета.** После каждой точки отчёт TS и отчёт Rust сравниваются
  **побайтово** (полный JSON: сводка + все находки с деталями). Расхождение = код 1.
- **Машина.** Windows 11, Ryzen 7 7800X3D, 32 ГБ RAM, NVMe; Node 24.20; Rust 1.100
  (release, `lto=true`, `codegen-units=1`).

## 5. Паритет (гейт)

Текущие данные (2026-11-22, `po/template.pot` = 40 256 записей):

| Язык | filled/total    | errors | warnings | Находок | Отчёт              |
| ---- | --------------- | ------ | -------- | ------- | ------------------ |
| `ru` | 17 888 / 40 256 | 725    | 959      | 1 684   | побайтово равен TS |
| `de` | 10 778 / 40 256 | 729    | 0        | 729     | побайтово равен TS |

Паритет по синтетике тоже побайтовый: 1× — 237 927 байт отчёта, 10× — 2 649 652 байта
(19 210 находок), 100× — 27 630 076 байт (200 920 находок). Сравниваются не только
числа: порядок находок, `rel`, `text` и текст `detail` совпадают символ в символ,
включая `duplicate-po` с `JSON.stringify`-экранированием и сортировкой по UTF-16.

| ----------- | -------- | --------------- | -------------- | ----------- | -------- | ---------- | ------- |
| 1× (`ru`)   | 7.0      | 328 / 298       | 89 / 86        | 3.68 / 3.48 | 23.5     | 81.9       | 1 684   |
| 10× (`ru`)  | 67.7     | 2 168 / 2 164   | 771 / 798      | 2.81 / 2.71 | 31.3     | 84.9       | 19 210  |

Коэффициент на каждом объёме — **не средний**: 3.5–3.7× на текущем корпусе, 2.7–2.8× на
10×, 2.6× на 100×. Абсолютные времена первого прогона шумят сильнее (кэш ФС на 700 МБ
входа): в отдельном прогоне 100× первый TS дал 31.1 с при 25.5 с во втором. Выводы — по
второму прогону, но оба приведены.

## 7. Что видно

- **Коэффициент устойчив.** 1× выигрывает ещё и за счёт старта (Rust ~5 мс против
  ~60 мс у Node), но и на 100× разрыв не растворяется: 2.6×.
- **Пропускная способность TS упирается в ~30 МБ/с**, Rust идёт 77–85 МБ/с. На 100×
  Rust проседает (77 против 85 на 10×) — это рабочий набор в памяти (4 млн записей),
  а не GC: запас всё равно 2.6×.
- **Память — самостоятельный аргумент.** TS на 100× падает на дефолтном heap; чтобы
  просто получить отчёт, нужно поднимать `--max-old-space-size`. Rust на том же входе
  работает без настройки. При `×100` «медленнее» — это ещё и «не запускается».
- **Экстраполяция на 10 языков при 100×:** TS ~4 мин против Rust ~1.5 мин на полный
  проход. На текущем 1× разница — секунды, и этого мало для миграции; решение даёт
  именно масштаб.

## 8. HTML-отчёт: остаётся в TypeScript

Rust отдаёт **JSON** (сводка + находки) и JSONL; HTML-дашборд не переносился.

Причины (KISS/DRY, без потери качества):

- рендер — это конкатенация строки на ~60 КБ: доли процента времени, узким местом не
  был и не станет;
- перенос разметки, CSS и фильтра в Rust создал бы **второй источник истины** для
  оформления; правки дизайна делались бы дважды;
- JSON — машинный контракт, он и нужен CI и паритету; HTML — презентация, ей место в TS.

Следствие для миграции: `npm run qa` остаётся тонкой TS-обёрткой (spawn Rust → JSON →
HTML). Если HTML не нужен (CI, пакетный прогон), достаточно одного Rust-бинаря.

## 9. Вердикт

**Мигрируем вычислительное ядро QA на Rust** (Rust считает и отдаёт JSON, TS остаётся
эталоном-оракулом и рендерит HTML).

Числа, на которых основано решение:

- ускорение **2.6–3.7×** на всех объёмах (порог проекта для миграции — ≥ 2×,
  порог предложения — ≥ 10 %);
- на 100× TS **не работает** без ручного увеличения heap (> 4 ГБ), Rust работает;
- паритет отчётов побайтовый на реальных `ru`/`de` и на синтетике 10×/100×, то есть
  миграция не меняет ни одной находки.

Порядок внедрения (в этой задаче не выполнялся — `package.json` вне зоны):

1. `npm run qa` зовёт `rust-qa` и рендерит HTML из его JSON; TS-версия остаётся в скилле
   как оракул (`npm run qa:ts` или флаг).
2. Паритетный тест (`scripts/qa_scaling_bench.mts --scales 1`, при желании — короткий
   `--scales 1` в CI) добавляется в `npm run test:qa`.
3. Rust-джоб CI — по образцу `docs/rust-vs-ts.md` §11 (toolchain 1.100, fmt, clippy, test).

### Условия пересмотра

1. **Коэффициент упадёт ниже 2×** на реальной нагрузке (например, TS получит потоковый
   парсер и сравняется) — вернуться на TS по тому же правилу.
2. **QA перестанет быть пакетным прогоном по большим объёмам** (останется 1× раз в
   релиз) — скорость перестанет быть причиной, остаётся TS.
3. **Появится инкрементальный QA** (дельты вместо полного прохода) — пересмотреть
   границу: возможно, Rust должен читать `.dat`/PO инкрементально, а не целиком.
4. **Правила начнут меняться чаще, чем раз в релиз** — цена второй реализации и
   паритета перевесит выигрыш; тогда переносим обратно.

## 10. Ограничения честности замера

- Масштабирование мерилось на `ru` (самый большой `.dat`), паритет — на `ru` и `de`.
  `de` на 10×/100× не гонялся: правила языка не меняют, а объём входа — тот же порядок.
- Синтетика — это повтор реальных записей с хвостом `~k`; она проверяет парсинг,
  правила и память на объёме, но не «новые» тексты. Хвост не содержит букв, поэтому
  доля кириллицы и проверка латиницы не искажаются.
- Пик памяти Rust отдельно не инструментирован (в задаче требовались время и МБ/с).
  Зафиксирован наблюдаемый факт: TS на 100× падает по heap, Rust — нет.
- Время включает старт процесса: для CLI это честная цена, для «чистого алгоритма» —
  верхняя оценка преимущества Rust на малых объёмах.
