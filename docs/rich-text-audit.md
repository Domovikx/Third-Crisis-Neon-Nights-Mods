# Аудит TMP-разметки `rich_text` в POT

Дата: 2026-11-23. Инструмент: `npm run rich:audit` (`.opencode/skills/extract-text/scripts/rich_audit.mts`).
Ничего не правилось и не удалялось — только классы, числа и примеры.

## Короткий ответ

Разметка в POT **цела**: наших поломок нет, а всё, что выглядит кривым, приходит таким из
данных игры. Из 2 374 записей с `rich_text` 2 370 совпадают с текстом ключа после снятия
тегов, и лишь 4 расходятся по содержанию (2 обрывка + 1 банковский пин + 1 шум).

Тегов всего четыре: `i` (1 701), `color` (1 197), `b` (151), `size` (65). Ни `font`, ни
`material`, ни `sprite`, ни неизвестных имён в POT не осталось.

## Что проверено отдельно: не ломаем ли теги мы сами

Сравнение POT с дампом (2 374 записи, тот же поиск по `msgid`):

- **2 355** совпали байт-в-байт после применения той же функции разворота цветов;
- **19** расхождений, и все объяснимы:
  - **5** — `<font=… material=…>` есть в дампе, вырезаны у нас (так и задумано: шрифт
    выбирает рантайм);
  - **13** — один и тот же текст встречается в разных объектах, победил первый по
    порядку (дедуп), поэтому разметка у копий отличается, а plain-текст совпадает;
  - **1** — разное содержание при одном ключе: `msgid ">"` (шум из `<< … >>`).

  Отдельно, внутри POT: **2 обрывка + 1 расхождение на символ** (банковский пин
  `… 7192>`) + **1 шум** — это и есть 3 предупреждения контракта `rich-fragment`
  плюс порог.

## Что исправлено по ходу аудита

**Порядок сканирования влиял на цвет.** `richText` разворачивался в момент добавления
строки, а карта `color_parser_list` наполнялась по мере чтения файлов. Объект, встреченный
раньше своей карты, остался бы с `<color=perversion>`, который TMP не понимает, то есть
реплика потеряла бы цвет. На текущем дампе таких записей не оказалось (`named-color` = 0),
но зависимость была реальной и тихой.

Исправлено: второй проход по готовому списку (`inventory.mts`), как в Rust-эталоне
(`finish()` после полного скана). Тест — «цвет разворачивается, даже если
`color_parser_list` встретился позже».

## Что решает владелец

1. **210 незакрытых / 12 перекрещенных / 4 лишних закрытия** — это данные игры, TMP их
   терпит. Вариант «дочинить разметку» означает правку контента: предлагаю **не трогать**
   (правило «внешний вид не повод переписывать»), но решение за владельцем.
2. **2 обрывка** (`you request them. >`, `your comfort, hon. … >`) — уже помечены
   `#, skip` правилом `fragment`: переводить хвост фразы бессмысленно.
3. **`<color=red|yellow|purple>`** — оставить как есть (TMP понимает), либо развернуть
   в hex для единообразия. Функционально это ничего не меняет.

## Обратный путь: как перевод возвращается в разметку

В PO перевод — это чистый текст без тегов. Игра собирает показ из `rich_text`:

```csharp
plainFromRich = Regex("<[^>]+>").Replace(richText, "");
if (richText.Contains(plainFromRich))
    richTranslation = richText.Replace(plainFromRich, translation);
```

То есть теги остаются, внутрь подставляется перевод. Работает это **только если
`plain` — цельный кусок `rich`**. Замер на 2 374 записях:

|                                                                                      | записей   | что видно в игре                 |
| ------------------------------------------------------------------------------------ | --------- | -------------------------------- |
| `plain` — цельный кусок `rich` (обёртка `<i>…</i>`, `<color>…</color>` вокруг всего) | **1 989** | перевод + исходная разметка      |
| теги **внутри** фразы (`<color>слово</color>` посреди текста)                        | **385**   | перевод без разметки этой строки |

Для 385 строк текст переведётся правильно, но цвет/курсив выделенного слова пропадёт:
`Replace` не находит `plain` и рантайм откатывается на голый перевод. Это ограничение
рантайма (нужен матчинг по токенам, а не по подстроке), а не POT.

Стык закрыт тестом `scripts/rich_roundtrip.test.mts`: зеркало алгоритма рантайма,
реальная строка с вложенными кавычками, негативные кейсы и потолок `inline` (385),
чтобы рост этого класса падал тестом, а не всплывал в игре.

## Разметка в PO: где хранится `rich_translation`

Решение владельца (2026-11-24): `rich_translation` живёт **в PO**, извлечённым
комментарием сразу за `rich_text` — у каждой записи с разметкой:

```po
#. src: dialog
#. rich_text: Hehe- That sounds- <color=#EB83FF>fun...</color>
#. rich_translation: Хе-хе- Звучит- <color=#EB83FF>весело...</color>
msgctxt "speaker:Zoey"
msgid "Hehe- That sounds- fun..."
msgstr "Хе-хе- Звучит- весело..."
```

- Контракт: `rich_text` = `msgid` + теги; `rich_translation` = `msgstr` + **те же**
  теги в том же порядке.
- Непереведённая строка держит пустую заготовку `#. rich_translation:` — гейт её
  разрешает (иначе свежие записи валили бы проверку).
- Пишут: `scripts/rt_backfill.mts` (бэкфилл/пересборка пар),
  `translate-local` (`applyMsgstrInPlace` — при любом переводе, `--improve` и
  `--repair`), `po_update`/`prefill` (Rust — сохраняют значение и сидят заготовку).
  Читает: `po2dat` → поле `rt` в `.dat`; рантайм предпочитает `rt` всему остальному.
- Старые `# rich_translation:` / `# rich:` больше не пишутся: бэкфилл перевёл их
  в `#.`-форму и снял дубли (на 2026-11-24 в `ru` таких было 479).

### Позиция тега не угадывается

Пропорциональный/«на глаз» перенос давал `<b> </b>` посреди фразы — игрок это
видит. Поэтому перенос делает парсер (`scripts/rich_tags.mts`):

- обёртка (`<i>весь текст</i>`) переносится точно — границы совпадают с краями;
- inline-пара ставится, только если её текст буквально найден в переводе
  (без учёта регистра, не короче 2 значимых символов, с буквой/цифрой);
- иначе пара выбрасывается, `rich_translation` = перевод без этих тегов, а запись
  получает флаг `#, rt-review` и ключ в отчёте «разметка требует человека».

Запрещено: тег вокруг пробела/пунктуации, пустая пара (`<i></i>`), открывающий
тег в конце строки. Гейт (`node scripts/rich_gate.mts`) считает такие артефакты
ошибкой.

### Текущее состояние (2026-11-24)

- Пар `rich_text` → `rich_translation`: **23 740** (2 374 × 10 языков), пустых
  заготовок 0 (все строки переведены), артефактов **0**.
- Разметка подтверждена (теги совпадают с `rich_text`): 22 340 пар; из них
  19 890 — обёртки, ~2 450 — inline с найденной позицией.
- На человеке (`#, rt-review`, ключи — `tmp/rt-review.json`): **1 400** пар,
  по языкам: zh 202, ru 30, es 123, pt 109, de 130, ja 214, fr 134, pl 130,
  ko 201, it 127. Причина одна: перевод переставил слова, подсвеченный фрагмент
  буквально не находится. Разметку там НЕ выдумываем.
- Битая разметка источника (`rich_text` без тегов — `msgid ">"` при
  `rich_text: «<< Declination processed… >>»`): 10 пар (по одной на язык),
  выведены отдельным списком, значение не затирается.
