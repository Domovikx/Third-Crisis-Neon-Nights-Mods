# [2026-11-22] Дамп: type tree для `*.assets` (96 % объектов `read_failed`)

Статус: READY

## Цель

Убрать корневую причину потери текста: в `level*.jsonl`, `sharedassets*.jsonl`,
`resources.jsonl` **все** объекты помечены `read_failed`, потому что в этих файлах нет
встроенного type tree. Из-за этого типизированные поля не читаются вообще, и текст
выживает только в `raw_strings` (байтовый скан), где его режут фильтры.

## Контекст (замер 2026-11-22, `tmp/rf_stats.mts`)

| Класс файлов                      | Объектов | `read_failed` | `raw_strings` строк | `dialogues[]` объектов |
| --------------------------------- | -------- | ------------- | ------------------- | ---------------------- |
| bundle (`StreamingAssets/aa`)     | 22 857   | 0             | 175 777             | 33                     |
| level (`level0..18`)              | 401 139  | 401 139       | 310 012             | 159                    |
| resource (`resources.*.resource`) | 128 342  | 128 341       | 197 403             | 290                    |
| sharedassets                      | 19 203   | 19 203        | 122 917             | 1 197                  |
| прочее                            | 6 933    | 6 933         | 34 172              | 0                      |

Итого: 555 616 из 578 474 объектов (96,0 %) `read_failed`; у 221 509 из них есть
`raw_strings`. Диалоги частично спасает байтовый скан JSON (`"Speaker":"…","Text":"…"`),
но типизированные UI-поля (`Description`, `DefaultDisplayName`, `UnlockHint`, `m_text`,
PlayMaker `choice.text`) в этих файлах недоступны — а именно там живут квесты, предметы
и выборы.

Пример: `level3.jsonl:41970` — объект с PlayMaker-выбором; в `raw_strings` видны
`Peek at them having sex.`, `Wait until they are done.`, `Leave.`, а типизированных
полей нет, потому что объект `read_failed`.

Цена бездействия: «видимый текст вне POT» ~970 строк (оценка), и это занижено — хвосты
полей в 96 % объектов просто не видны.

## Что сделать

1. Решить, откуда брать схемы встроенных классов Unity: свой минимальный набор (только
   типы, которые несут текст: `MonoBehaviour` с известными скриптами, `TextMeshPro*`,
   `PlayMakerFSM`, `ScriptableObject`) или генерация из репозитория typetree
   (UnityPy-совместимый формат). Второй вариант лучше, если лицензия позволяет.
2. Реализовать чтение выбранных полей в Rust-декодере (и/или TS-эталоне) с проверкой
   границ и без падения на неизвестных типах.
3. Мерить: сколько объектов перестали быть `read_failed`, сколько `strings`-значений
   появилось, сколько из них человекочитаемых, сколько попало в POT после задач
   `pot-typed-ui-fields` и `pot-ui-filter-narrowing`.
4. Паритет с эталоном: для файлов, где type tree уже есть (bundle), поведение не должно
   измениться; POT не должен потерять ни одной старой записи.
