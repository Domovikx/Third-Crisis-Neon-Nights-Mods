# [2026-11-21] po2dat: gated-вариант не должен скрывать ручной перевод

Статус: READY

## Задача от пользователя

«перепроверять все экстракторы и то как формируется pot po… большое ревью
с оптимизанией и кайдзен делаем.»

## Цель

Исправить поведение `po2dat.mts`, при котором строка с флагом
`auto-normalized` может скрыть из игры уже готовый ручной перевод того же
текста.

## Контекст (проверено 2026-11-21)

- `buildDat` группирует записи по `msgid`, сортирует заполненные по
  `refKey` (earliest-ref-file-wins) и смотрит на флаг **только у победителя**
  (`filled[0]`).
- Если у текста есть две пары — `#: translations/a.yaml` с флагом
  `auto-normalized` и `#: translations/b.yaml` без флага, — сортировка выбирает
  `a.yaml`, гейт срабатывает и текст не попадает в `.dat` вообще, хотя ручной
  перевод существует.
- На данных 2026-11-21 флагов `auto-normalized` в `po/*.po` нет (0 штук),
  поэтому сейчас эффекта нет. Риск появится, когда `prefill_po` вернётся
  после порта.
- Поведение зафиксировано характеризационным тестом
  `buildDat: gated-вариант, победивший сортировку, скрывает текст целиком`.

## Что сделать

1. Решить правило: гейт должен выбирать первый **не-gated** заполненный
   вариант, а gated использовать только если других нет.
2. Реализовать в `buildDat` (5–8 строк), не меняя `refKey`-порядок для
   остальных случаев.
3. Переписать характеризационный тест в проверку нового поведения + добавить
   кейс «только gated» (остаётся скрытым).
4. Проверить паритет на реальных данных: для `po/*.po` (10 языков) `.dat`
   не меняется (флагов нет), отчёт `gatedAutoNormalized` по-прежнему 0.
5. Обновить комментарий в `po2dat.mts` и `extract-text/SKILL.md`
   (сейчас там сказано, что гейт смотрит только на победителя).

## Приёмка

- Тест «есть ручная пара → ручной перевод уезжает, gated игнорируется» зелёный.
- Тест «только gated → строка не уезжает» зелёный.
- `.dat` для ru/de/pl/es/… байт-в-байт прежний.
- `npm test`, `npm run test:e2e` зелёные.

## Вне рамок

- Изменение правил `earliest-ref-file-wins`.
