## 3. Эмоции

### 3.1 Где и в каком формате

- Хранение — `#. emotion:` в `po/template.pot`, одна строка на запись, рядом с
  `#. src:` (единственный холд тона; в `po/*.po` тон не попадает — см. 4.5).
- Формат — **английский**, 2–6 слов, состояние диктора при доставке, с заглавной,
  без кавычек и точки. Примеры: `Quietly observing, a little flustered`,
  `With commanding authority`, `Softly, as an inner thought`.
- Почему английский: VoxCPM2 подаёт тон стилевым префиксом `(<emotion>)text`
  (`voxcpmworker.py:8-11,150-167`); русские/китайские инструкции дают акцент
  (проверено в TSSR).
- Правила качества — скилл TSSR `.opencode/skills/emotion-tag/SKILL.md`
  (7 правил: состояние, а не пересказ; не шаблонить; `none` запрещён; и т. д.).

### 3.2 Какие категории получают тон

| Служебные `raw:*`/`us`/`bundle` | 6 610 | нет | не текст для игрока       |

Итого **7 199 тонов**; у каждой озвучиваемой записи тон обязан быть (TSSR:

рассказчика», для диалога — «состояние говорящего».

### 3.3 Аудит

Портируется из TSSR (`emotion_audit.mts`); правила формата — одна реализация
(`violationsOf`) на весь TCN:

```bash
npm run emotion:audit          # POT: нарушения + покрытие + однородность
npm run emotion:audit -- --draft   # черновик tmp/emotions_tagged.json до оверлея
```

Проверки:

- **формат**: пусто, кириллица, CJK, `none`, >6 слов, 1 слово, не с заглавной,
  кавычки (реализация правил — одна, `violationsOf`, как в TSSR);
- **покрытие**: 7 199/7 199, ноль тонов на исключённых категориях;
- **однородность**: число уникальных тонов, топ-1 и его доля, доля «один раз»
  (сигнал шаблонного ответа LLM);
- **структура POT** (инвариант 16 в `pot_invariants.mts`): один `emotion:` на запись,
  без пустых и многострочных значений, нет тона на `#, skip` и вне `src: dialog`.

Порогов «в коде» нет (KISS): приёмка — числа в отчёте + решение владельца.
Ориентиры TSSR после ремонта: нарушений 0, топ-1 2,3 %, «один раз» 66 % словаря.

### 3.4 Время на 7 199 строк

**Замера нет** — LLM не запускалась (условие задачи; порты 8080/8000/1234 = `000`).
Поэтому первый шаг разметки — замер на 50 строках, а не экстраполяция с потолка.

Протокол замера (50 строк, те же 50 на все прогоны):

1. Поднять бэкенд (LM Studio `qwen3.5-9b`, `127.0.0.1:1234`), прогреть 2 запросами.
2. Взять 50 строк из набора озвучки стратифицированно: 25 диалог / 25 нарратив,
   разные спикеры, 10 длинных (>150 симв.).
3. Прогнать классификатор (`--limit 50`) и замерить: общее время, с/строку,
   строк/мин, число пустых ответов, таймаутов, нарушений формата.
4. Повторить на выбранной конкурентности (1 / 4 / 8 воркеров) — параллельность
   на одной GPU не линейна, её нельзя домножать теоретически.
5. Записать в задачу измеренные `с/строка` и `строк/мин`; только после этого
   оценивать полный прогон.

Пересчёт от измеренного темпа (арифметика, не прогноз качества):

| с/строка (замер) |   1 поток | 4 потока | 8 потоков |
| ---------------: | --------: | -------: | --------: |
|             0,50 |  60,0 мин | 15,0 мин |   7,5 мин |
|             0,75 |  90,0 мин | 22,5 мин |  11,3 мин |
|             1,00 | 120,0 мин | 30,0 мин |  15,0 мин |
|             1,50 | 180,0 мин | 45,0 мин |  22,5 мин |

Документированный базис для сравнения: перевод TSSR — 400 строк за 162 с
(2,47 строк/с) на Index-Translate-9B с 8 воркерами
(`docs/translate-backend-perf.md`). Для эмоций промпт короче ответа, но запрос
последовательный (как `emotion_tag.mts` в TSSR), поэтому 50-строчный замер нужен
именно на нашей конфигурации.

### 3.5 Риск галлюцинаций и приёмка человеком

Риски (каждый уже наблюдался в TSSR):

- **пересказ содержания вместо состояния** («Pained yet yielding» — описание эмоции,
  а не доставка);
- **шаблонный дефолт**: инцидент «26 % Curiously observing» — лечится контекстом
  (спикер + соседние строки) и запретом переиспользовать тон;
- **тон не по сцене**: модель не видит сцену, если дать только текст; в TCN POT
  отсортирован по `msgid`, поэтому «предыдущая строка по файлу» — не сосед по сцене;
  контекст берём из дампа (порядок `dialogues[]`), иначе только спикер + строка;
- **пол/лицо**: Зои говорит от первого лица; тон не должен звучать как обращение;
- **18+**: в сценах с насилием/сексом модель может «смягчить» тон — проверять
  выборкой.

Меры:

- промпт с контекстом (спикер, 1 строка до/после из сцены, класс «диалог/нарратив»);
- `temperature 0,3`, `reasoning_effort: "none"` (иначе qwen3.5 возвращает пустой
  `content` — грабли LM Studio);
- черновик резюмабельный, чекпоинт каждые 200 строк, повтор на пустой/битый ответ;
- аудит формата и однородности — до оверлея;
- опционально судья-выборка (LLM-балл «тон подходит строке/спикеру»), как в TSSR;
- **приёмка человеком**: 100 случайных строк (стратифицированно по спикерам) +
  100 % строк демо-сцены; критерий — не меньше 90 принятых из 100, остальные
  переразметить точечно.

## 4. Эмоции на уровне POT: оверлей, а не генератор

Да, так можно и так правильнее: **LLM не живёт внутри Rust**. Rust получает готовый
JSON и применяет его детерминированно. Ниже — что есть сейчас и что добавить.

### 4.1 Что есть в `rust-l10n potgen` сейчас

Короткий ответ: **поддержки оверлея эмоций нет**, её нужно добавить; механизм —
ровно как у `--skip-ids` (данные, не код).

Проверено по коду:

- `tools/rust-l10n/src/main.rs:30-33` — флаги potgen: `--update`, `--dump`, `--out`,
  `--created`, `--policy`/`--no-policy`, `--skip-policy`/`--no-skip-policy`,
  `--skip-journal`, `--root`; отдельно `--skip-ids`/`--no-skip-ids`
  (`main.rs:221-260`).
- **Флага `--emotions` нет**: поиск слова `emotion` по `tools/rust-l10n/src`,
  `tools/rust-l10n-core/src` и `tools/rust-l10n/tests` даёт 0 совпадений.
- Образец для копирования — `--skip-ids`: `parse_skip_ids` → `load_skip_ids` →
  `discover_skip_ids_path` → `apply_skip_ids` (`potgen.rs:819-916`), применение
  после правил (`potgen.rs:1345-1365`), рендер комментариев
  (`potgen.rs:1128-1150`), `Slot` (`potgen.rs:934-939`).
- Слоты каталога — `(msgid, msgctxt)`; комментарии записи рендерятся в порядке
  `src:`, `skip:`, затем `rich_text:`/`repaired:`.

### 4.2 Схема данных

```text
классификатор (TS + локальная LLM)
        │  tmp/emotions_tagged.json   (черновик, резюмабельный)
        ▼
config/emotions.json                 (артефакт, в git; ключ — msgid)
        │
        ▼
rust-l10n potgen --emotions <path>   (или discovery config/emotions.json)
        ▼
po/template.pot  с  #. emotion: …
        ▼
voice_batch (будущий) читает тон из POT — второго холда нет
```

Формат `config/emotions.json`:

```json
{
  "_comment": "Тон диктора: msgid -> English delivery instruction. Генерирует .opencode/skills/extract-text/scripts/emotion_tag.mts; potgen ставит #. emotion:.",
  "emotions": {
    "\"COCK\"...? Really...?": "Incredulously, with a dry smirk",
    "...": "..."
  }
}
```

- ключ — **точный `msgid`** (не md5): Rust-зависимость `md-5` не нужна, диффы
  читаемы, а uid понадобится только для имён аудиофайлов (отдельный шаг). Дублей
  msgid в наборе нет (7 199 = 7 199), потерь от такого ключа ноль;
- ключи отсортированы, JSON печатается `renderJson` (prettier), как
  `config/pot-skip-ids.json` → побайтовая воспроизводимость;
- размер: ключи набора — 354 523 байта; файл при среднем тоне 25 символов —
  649 682 байта (354 523 + 7 199 × 41 на строку и обёртку); POT вырастет на
  273 562 байта (`#. emotion: ` + 25 + перевод строки на запись).

Почему не `.mts`-модуль (как `pot-skip-ids.mts`): содержимое генерируется моделью
и ревьюится как данные (7 199 записей), а не пишется рукой; типизация даёт только
`Record<string, string>`. Источник истины — JSON + тест-страж, а не 7-тысячестрочный
TS-файл (KISS). Если позже появится ручная правка массово — можно обернуть в `.mts`
без изменения формата.

### 4.3 Что добавить в Rust (по образцу `--skip-ids`)

1. `PotgenOptions.emotions: PolicySource` (Default/Disabled/Path), как `skip_ids`.
2. `parse_emotions(text, source) -> BTreeMap<String, String>`: объект, поле
   `emotions`, только `_`-поля сверх него; ключ непустой; значение непустое, без
   `\n`/`\r`, не длиннее 120 символов (формат тона проверяет TS-аудит, чтобы не
   было двух реализаций правил).
3. `load_emotions(path)` (нет файла — `None`), `discover_emotions_path(root)` —
   `config/emotions.json` вверх по дереву, как у skip-ids.
4. `Slot.emotion: Option<String>`.
5. `apply_emotions(catalog, map) -> (applied, not_voiceable, unused)`; применять
   только к записям с `slot.src == "dialog"`, `msgctxt != "speaker-name"` и
   `slot.skip.is_none()`. Остальные ключи — в счётчик «не озвучиваемых», ключи вне
   POT — предупреждение (как «устаревшие» у skip-ids).
6. Рендер: после `src:` и `skip:` добавлять `emotion: <тон>` перед `rich_text:`.
7. CLI: `--emotions <p>` и `--no-emotions`; добавить `--emotions` в `PATH_FLAGS`
   обёртки `scripts/text_cli.mts:43-51` и в `USAGE`.
8. Тесты (Rust): парсинг (хороший/битый JSON, пустое значение, перевод строки),
   применение (диалог/нарратив/`skip`/UI), `unused`-счётчик, детерминизм (два
   прогона — байт-в-байт), мини-дамп с синтетическим оверлеем — золотые байты
   с `--created`.
9. `scripts/pot_invariants.mts`: инвариант 16 (`emotion-syntax`,
   `emotion-duplicate`, `emotion-on-skip`, `emotion-on-non-dialog`) + обновление
   `docs/pot-contract.md` (снимок чисел и описание).
10. `scripts/emotion_audit.mts` + `npm run emotion:audit` (раздел 3.3) плюс
    страж `config/emotions.test.mts`: схема (`emotions` + `_`-поля), ключи
    отсортированы, нет дублей ключей в сыром тексте, покрытие = набор озвучки.
11. Классификатор `.opencode/skills/extract-text/scripts/emotion_tag.mts`:
    кандидаты = набор озвучки (7 199), контекст из дампа, черновик, `--resume`,
    `--limit`, `--dry-run`, `--only-invalid`.

### 4.4 Детерминизм и золото

- POT детерминирован, **если заморожен оверлей**: одинаковые дамп + политики +
  `config/emotions.json` дают байт-в-байт тот же файл. Недетерминизм LLM
  (temperature 0,3) не влияет: в сборку попадает только закоммиченный JSON.
- Детерминизм проверяется существующим тестом
  `scripts/text_parity.test.mts` («Rust potgen на реальном дампе ==
  `po/template.pot`»): он запускает potgen с дефолтами, то есть с оверлеем.
  Правка `config/emotions.json` без перегенерации POT = красный тест. Это и есть
  «золотые хэши пересобираются осознанно».
- Полное золото POT — `.opencode/skills/extract-text/test_data/pot-golden.json`:
  сейчас `18 445` записей, `1 853 904` байта,
  `sha256 2bdb8931851b878b26581cdfcc3c89cc90d459dfcdba626efdb89df91f1c4b14`.
  После первого оверлея поля `bytes`/`sha256` (и, если меняется число записей,
  `entries`) обновляются в том же коммите, что и POT. Сейчас пересчёт ручной;
  чтобы не ошибиться, в `text_parity` добавляется режим `POT_GOLDEN_UPDATE=1`
  (иначе `sha256` и размер считаются вручную и легко разъезжаются).
- Мини-золото (`pot-golden-small.pot`) не должно зависеть от репозиторного
  оверлея: в его команду добавляется `--no-emotions` (сейчас там уже
  `--no-policy --no-skip-policy --no-skip-ids`); Rust-тест мини-дампа явно ставит
  `emotions = Disabled`, как уже делает для policy.
- Порядок осознанного обновления: правка JSON → `npm run potgen -- --update` →
  пересчёт `pot-golden.json` → `npm run pot:check` / `npm run test:golden` /
  `node --test scripts/text_parity.test.mts` → `npm run po:update` всех языков
  (проверить, что тон не утёк, см. 4.5) → дифф POT/PO в одном коммите.
- `.dat` не меняется: `po2dat` берёт из POT только `rich_text`
  (`tools/rust-l10n/src/po2dat.rs:58-62`), комментарий `emotion:` игнорируется.

### 4.5 Обязательный фильтр: `po_update` не должен копировать тон

Найдено при проверке: `po_update` переносит **все** комментарии POT в каждый
`po/<lang>.po` (`tools/rust-l10n/src/po_update.rs:436-455`,
`with_rich_translation`). Сейчас в `po/ru.po` уже лежат `#. src:` (14 365) и
`#. rich_text:` (2 374). Если просто добавить `#. emotion:`, то
`npm run po:update` размножит 7 199 тонов на 10 языков (71 990 строк, несколько
МБ) — это ломает принцип «тон живёт только в POT» (в TSSR тон из `po/*.po`
убирали специально).

Поэтому в тот же шаг входит:

- фильтр `emotion:` в `po_update` (не копировать), как `with_rich_translation`
  уже фильтрует `rich_translation:`;
- тест: POT с тоном → `po_update` → в `po/<lang>.po` нет `#. emotion:` и файл
  побайтово совпадает с текущим (при тех же переводах).

### 4.6 Плюсы и минусы оверлея

| Плюсы                                                          | Минусы                                                          |
| -------------------------------------------------------------- | --------------------------------------------------------------- |
| Один источник тона — POT; генератор не знает про вторые холды  | Два шага: сначала классификатор, потом potgen                   |
| Детерминизм сборки; LLM может быть любой и недетерминированной | Каждая правка тона меняет POT и золотой хэш (осознанный коммит) |
| Аудит и откат: удалить ключ/`--no-emotions` — и тона нет       | POT растёт (273 562 байта при тоне 25) и диффы шумят            |
| Тон переживает обновление игры, пока `msgid` не изменился      | Изменился текст → новый ключ → тон теряется (аудит покажет)     |
| Ревью в одном JSON: видно все тоны, легко сравнивать           | Нужны guard-тесты, иначе POT и JSON разъезжаются молча          |
| Нет сети/GPU в сборке: Rust только читает файл                 | Классификатор обязан быть резюмабельным (7 199 записей)         |

Отдельно: оверлей **не умеет** разный тон для одинакового текста в разных контекстах
(ключ — `msgid`). В наборе таких дублей 0, поэтому сейчас это не потеря; если
появится — ключ расширяется до `(msgid, msgctxt)` без смены механики.

### 4.7 Локализация тона

- В POT — **только английский**: это инструкция модели, а не текст для игрока;
  VoxCPM2 получает `(<emotion>)text`, русская инструкция даёт акцент.
- `--emotion-ru` (как в TSSR) нужен только для манифеста/ревью человеком, а не для
  генерации. В TCN манифеста ещё нет, поэтому **сейчас не делаем** (YAGNI): отчёт
  аудита показывает английский тон рядом с EN-строкой и её `msgstr` из `ru.po` —
  этого достаточно для вычитки.
- Если владельцу нужен русский глоссарий для ревью — переводим не 7 199 строк, а
  уникальный словарь тонов после приёмки (один раз), и держим его отдельно от POT.
