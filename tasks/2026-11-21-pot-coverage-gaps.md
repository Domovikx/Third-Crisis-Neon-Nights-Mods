# [2026-11-21] Закрыть пробелы POT: вернуть потерянный текст игры

Статус: READY

## Задача от пользователя

«перепроверять все экстракторы и то как формируется pot po всего ли там достаточно…
вобщем большое ревью с оптимизанией и кайдзэн делаем.»

## Цель

Сделать POT полным: каждая строка, которую игрок видит на экране, должна иметь
запись в `po/template.pot`. Сейчас ~900 уникальных человекочитаемых строк дампа
не попадают в шаблон (2,7 % от 33 271 записи), из них около 512 выглядят как
реальный текст игры (квесты, описания предметов, тултипы, релиз-ноты, диалоги).

## Контекст (замер 2026-11-21)

- Дамп: 319 МБ, 477 872 строки JSONL, 131 чанк + summaries.
- POT: 33 271 запись; инвентарь 38 973 строки.
- 900 уникальных предложений дампа отсутствуют в POT (сверка с нормализацией
  числовых префиксов `NN-` и пунктуации).
- По первой сработавшей эвристике `isUiString`:
  - `dot+upper` (точка + заглавная в первых 5 code points) — 459;
  - `length>50` — 348;
  - `parens` — 205;
  - отладочные паттерны (`don't`, `is not`, `handles`…) — 26.
- Отдельный срез: 92 652 объекта (19,4 %) помечены `read_failed` (UnityPy не
  разобрал TypeTree). В них 196 864 raw-строки, и 454 из 900 пробелов
  приходятся именно на такие объекты.
- `summaries.global_strings` (до 500 на ассет, 132 806 строк всего) не читается
  `inventory.mts` вовсе.
- Примеры потерянного: «This will unlock the Afterglow employee area.»,
  «Find Jasmine in the Glowing Hole.», описания одежды из BluFit/Hi-Thread,
  «You've reached the end of the free demo…» (эта строка есть в POT другим
  путём — проверять каждую индивидуально, не грести всё подряд).

## Что сделать

1. Выгрузить список пробелов повторяемо: скрипт `tmp/` → отчёт с причиной и
   `asset/path_id/type` для каждой строки (сейчас `inventory` не сохраняет
   контекст отбракованных строк — понадобится отдельный диагностический проход
   или флаг `--report-rejected`).
2. Разделить три источника и решать по отдельности:
   - `read_failed` объекты: попробовать `read_typetree` с fallback на raw-JSON
     (диалоги ANToolkit ищутся паттерном `"Speaker":"…","Text":"…"` — часть
     строк там ловится, но без типа/спикера);
   - длинные UI-строки: поднять/убрать лимит 50 для `raw`-строк, проверив шум
     на 20–30 примерах (описания предметов должны войти, имена ассетов — нет);
   - `dot+upper`: сузить эвристику до «похоже на C#-идентификатор» (нет
     пробела ИЛИ ≤3 сегментов без пробелов), а не «есть точка + заглавная».
3. `summaries.global_strings`: оценить как отдельный источник (только строки,
   которых нет в POT и которые проходят строгий фильтр «предложение»), включать
   только с ревью — там много обрывков бинарного скана.
4. Пересобрать POT и **доказать паритет не сломан**: `potgen.mts --out
tmp/parity-check.pot` → сверка с `po/template.pot` даст ожидаемый дифф
   только в новых записях; старые записи не должны исчезнуть.
5. Прогнать `po2dat` на ru и убедиться, что новые записи не ломают словарь
   (добавляются с пустым `x`, рантайм их игнорирует до перевода).

## Приёмка

- Повторяемый отчёт: число пробелов до/после, разбивка по причинам.
- POT содержит все строки из списка «игрок видит» (выборка 50 вручную).
- **Релиз-ноты и титры включены** (решение владельца 2026-11-21: «всё, включая ноты»),
  даже если объём большой и текст быстро устаревает.
- Старые записи POT не потеряны: дифф только аддитивный.
- `npm test`, `npm run test:e2e` зелёные; `po2dat` на ru даёт ≥ прежних строк.
- Отчёт о решении дописан в этот файл.

## Находка 2026-11-22: три уровня вообще не дампятся

Python-дампер обходит только `level0..15` и `sharedassets0..15`, а в установке
**19 уровней** (`level0..18`, `sharedassets0..18`). Проба UnityPy по «забытым»:

- `level16` — 8 936 объектов, 753 уникальных текстовых строк; среди них
  `<color=purple>Explore the train.</color>` — то есть **цели квестов**.
- `level17` — 37 190 объектов, 3 295 строк: `1 - Check ready for hand in Parts to Lio`,
  `2 - Enter Waiting Area` и т.п.
- `level18` — 23 810 объектов, 2 566 строк (имена объектов, вероятно диалоги).

Итого ~70 000 объектов и тысячи строк мимо POT — это, скорее всего, и есть основная
часть «~900 потерянных строк» из отчёта ревью (там считались файлы 0..15).

**Правильное решение — не расширять диапазон до 18, а читать список сцен из
`globalgamemanagers`**: тогда следующий апдейт игры с `level19` не потеряется молча.
Это же снимает вопрос «почему 16, а не 18».

Приёмка для этого пункта: дампер обходит все сцены из `globalgamemanagers`; в отчёте
есть список сцен и число объектов по каждой; POT вырос на строки из ранее пропущенных сцен.
