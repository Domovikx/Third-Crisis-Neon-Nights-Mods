# [2026-11-21] Определить судьбу python-острова `dump-assets` (UnityPy)

Статус: READY

## Задача от пользователя

Часть общей задачи: «максимально запускаем миграцию на ts mts вместо питона» — при этом
в `AGENTS.md` зафиксировано, что Python допустим только там, где физически не обойтись.

## Цель

Зафиксировать решение по единственному оставшемуся Python-модулю и не потерять его работоспособность
при переезде: дампер Unity-ассетов должен продолжать работать из нового репозитория, а его тесты —
жить в CI.

## Контекст

- `dump_assets.py` (1334 строки) + `dump_sqlite*.py` — читает `.assets` и `.bundle` игры через
  `UnityPy` (Python-библиотека разбора Unity-сериализации).
- TS-эквивалента нет; писать свой парсер Unity = месяцы и высокий риск.
- Выход дампера — JSONL в `tmp/dump/` (~660 MB), от него зависят `potgen`/`find_source`.
- `dump_assets.test.py` (368 строк) требует `UnityPy`.

## Ресёрч 2026-11-22: чем можно заменить UnityPy

Что реально существует (проверено в вебе, ссылки ниже):

- **Rust.** Есть крейты `unity_asset`, `unity_asset_binary`, `unity_bundle_assets`, `unityfs`
  (docs.rs). Умеют AssetBundle + SerializedFile. Зрелость не подтверждена: узкие крейты,
  мало пользователей, документация на уровне «структура распарсена».
- **TypeScript.** `fatal10110/unity-asset-reader` — парсер на TS, читает бандлы в браузере и
  Node, текстуры декодирует через WASM. Новый проект, покрытие полей не проверено.
- **C#.** Два зрелых пути: `Unity-Technologies/UnityDataTools` (официальная библиотека Analyzer +
  CLI) и `AssetsTools.NET` (на нём вырос AssetStudio/UABEA). Формат Unity они знают лучше всех,
  кроме самого редактора.
- **Python.** `UnityPy` 1.25.0 — то, что уже работает и даёт наш JSONL.

Важно: даже при готовом парсере **наши 1350 строк — это не парсинг, а извлечение**: какие
MonoBehaviour-поля читать, как склеить `raw_strings`, как отличить диалог от ассета, какие
`settings_keys` брать. Этот слой переносится в любой язык и его надо перепроверять на дампе.

## Вердикт по замене

- **Rust — преимущества нет.** Дампер запускается редко (раз на апдейт игры), 30–60 с, узкое место —
  распаковка LZ4/LZMA и разбор объектов, а не язык. Rust даст ускорение на CPU-bound части, но
  добавит второй тулчейн (cargo/rustup), отдельный CI-джоб и бинарники — цена без выгоды.
- **TS — теоретически можно**, но это свой парсер формата Unity поверх незрелой библиотеки:
  высокий риск тихо потерять строки (а мы уже знаем, что потеря 900 строк незаметна). Выгода —
  «ноль Python в репе», то есть эстетика.
- **C# — единственная осмысленная замена**, если Python мешает принципиально: язык уже в проекте
  (`build.mts` компилирует C# через `csc.exe`), а `UnityDataTools` — официальная библиотека.
  Но это тоже большой порт с повторной проверкой извлечения на 319 МБ дампа.
- **Оставить остров — рекомендуемый вариант (KISS/YAGNI).** Дампер изолирован: отдельный CI-джоб,
  `ruff` только по его папке, версии зафиксированы в `requirements.txt`. Пересматривать только при
  реальной потребности: например, если дампер надо отдавать пользователям без Python.

## Что сделать

1. Ресёрч (обязательно, с вебом):
   - есть ли на 2026 год жизнеспособные JS/TS-библиотеки разбора Unity assets (искать по
     «unity assets parser typescript/node», «AssetStudio alternative javascript»);
   - можно ли вызывать UnityPy из TS через отдельный процесс (уже так и есть) и что это стоит по
     скорости/сложности;
   - что даёт `.bundle` (LZ4HC) разбор — есть ли готовые реализации вне Python.
2. Сравнить варианты (уже сделано в разделе «Ресёрч»): (A) оставить Python-остров,
   (B) TS-парсер, (C) Rust-крейты, (D) C# на `UnityDataTools`/`AssetsTools.NET`.
3. Подтвердить решение (по умолчанию — A) и добить изоляцию: отдельный job в CI, `ruff` только по
   папке острова, версии в `requirements.txt` (сделано 2026-11-22: `UnityPy==1.25.0`, `PyYAML==6.0.3`).
4. Проверить, что дампер запускается из нового репозитория и находит игру через
   `scripts/game_dir.mts` (или через явный `--game`), а не «рядом с репо».
