# MAP — extract-text (факты и грабли)

Проверено на реальном дампе (319 МБ, 477 872 строки, 131 чанк + summaries) и
`po/template.pot` (33 271 запись) 2026-11-21.

## Готчи

- ⚠️ **Числа POT не сходятся с файлом дампа** → `potgen` печатает
  `inventory items: 38 973`, а не число строк дампа (477 872): это уже
  отфильтрованный инвентарь (диалоги + бандлы + UI + FSM + settings + спикеры)
  → проверено прогоном 2026-11-21 → не использовать `scanned` как «сколько
  строк в дампе» и не пугаться разницы.

- ⚠️ **`path_id` теряет точность** → Unity-хэш 64-битный, `JSON.parse` округляет
  значения > 2^53 → в дампе **6 485 уникальных** таких `path_id` (проверено
  2026-11-21) → `inventory` берёт id регуляркой из сырой строки и сравнивает
  `BigInt`; не заменять на `obj.path_id` в коде.

- ⚠️ **Паритет POT проверяется только с двумя нормализациями** → разница
  `POT-Creation-Date` (время) и `CRLF`→`LF` (Python на Windows пишет `\r\n`)
  → проверено: `npm run potgen -- --dump tmp/dump-after --out tmp/parity-check.pot`
  даёт **1 853 904 байта** (18 445 записей), идентично `po/template.pot` кроме
  даты → любая другая нормализация (порядок, пробелы) прячет настоящий дифф.

- ⚠️ **`--out` не изолирует статистику** → `potgen` всегда читает ключи
  старого `po/template.pot` (для счётчиков `new`/`vanished`), даже когда пишет
  в `tmp/...` → это только счётчики, состав каталога не зависит.

- ⚠️ **Заголовок POT говорит «generated by potgen.py»** → оставлено намеренно:
  шапка входит в байт-паритет с прежним шаблоном, смена строки = шум в
  диффе без пользы → не «исправлять» имя файла в `potHeaderLines`.

- ⚠️ **`po2dat` гейт смотрит только на победителя** → при двух парах одного
  текста (`#: translations/a.yaml` gated и `b.yaml` ручная) сортировка
  выбирает первую, и gated-флаг скрывает текст целиком → проверено
  характеризационным тестом 2026-11-21; на данных 2026-11-21 флагов
  `auto-normalized` в `po/*.po` нет (0) → исправление поведения =
  `tasks/2026-11-21-po2dat-gated-order.md`.

- ⚠️ **В POT нет `#:` refs** → провенанс (ассет/сцена) не пишется, поэтому
  `po2dat.refKey` у всех записей `~` и дубли одного текста разрешает порядок
  файла; провенанс ищется по дампу (`npm run find:source -- "<msgid>"`) →
  переводчику доступны `msgctxt` (спикер), `rich_text` и `#. src`, но не сцена
  в каждой строке → это часть задачи
  `tasks/2026-11-21-pot-context-for-translators.md`.

- ⚠️ **Дедуп диалогов разный на двух уровнях** → `DumpScanner` дедупит
  `(text, speaker)` в пределах ОДНОГО объекта дампа (как extractor.py),
  `potgen` — по `(msgid, msgctxt)` глобально → не удивляться, что инвентарь
  больше POT; `merged twins` — удалённые ui-двойники (`tmp/potgen` печатает
  счётчик; после политики отбора он снимается до неё — на здоровых данных
  сравнивать их нельзя, проверено 2026-11-22).

- ⚠️ **Запись `.dat` атомарная, байты прежние** → `writeDat` пишет `.part` и
  делает rename; содержимое не изменилось (паритет с po2dat.py) → проверено
  тестом «запись атомарная» 2026-11-21.

- ⚠️ **`readJsonl` молча глотает битые строки** → как `iter_jsonl_objects`:
  обрезанная строка дампа не валит прогон, но и не считается → если POT
  внезапно «похудел», сначала `wc -l` дампа и повторный дамп, а не правка
  инвентаря.

- ⚠️ **Порядок файлов не как Python `sorted()`** → `compareFileNames` сортирует
  без регистра (поведение Windows), Python — с регистром → на реальном дампе
  POT совпал байт-в-байт (2026-11-21) → при новых именах файлов с разным
  регистром перепроверять паритет, а не «оптимизировать» функцию.

- ⚠️ **Разные переводы у разных спикеров схлопываются в `.dat`** → рантайм ищет
  по голому тексту, `po2dat` группирует по `msgid` и оставляет победителя
  earliest-ref, печатая `DUPE` → проверено 2026-11-21: 54 группы в `po/ru.po`
  (0,3 %), пример «Your loss.» → это ограничение рантайма, а не сборки →
  при переводе помнить, что вариант выбирается порядком файла; чинить только
  через C# (вне рамок).

- ⚠️ **`#. src:` — путь доставки, а не «где ещё встречается»** → метка ставится
  при первом вхождении `(msgid, msgctxt)` в каталог; у строк, лежащих и в
  `dialogues[]`, и в бандле, порядок дампа решает `dialog` vs `bundle`
  (1 172 записи на `tmp/dump-after`, проверено 2026-11-22) → при политике
  отбора помнить о перекрытии классов; менять правило только вместе с
  TS+Rust и паритетом.

- ⚠️ **`settings` vs `us` различаются по ключу, а не по тексту** → в
  `summaries.jsonl` DLL-строки (`format: dotnet_us_heap`) несут в
  `settings_keys` и настоящие настройки (`key: Settings.*`), и автономные
  UI-строки из `#US` (`key == display`) → правило: `Settings.*` = `settings`,
  иначе `us`; для `.resource`/ассетов ключи всегда `Settings.*` (проверено
  2026-11-22).

- ⚠️ **`po/template.pot` не проходит `pot:check` до перегенерации** →
  файл сгенерирован до провенанса, инвариант 14 даёт `src-missing` на каждой
  записи (40 256) → это ожидаемо (CI: `pot:check || true`); реальные тесты
  зовут `checkPot(..., { requireSrc: false })`, новый POT проверяется без
  флага; после перегенерации на шаге политики — убрать opt-out.

- ⚠️ **Порядок полей в `field:` метке должен совпадать в TS и Rust** →
  в дампе ключи `strings`/`fields` отсортированы генератором, но синтетика в
  тестах может быть в другом порядке → TS сортирует `compareCodePoints`,
  Rust полагается на `serde_json::Map` (BTreeMap) → при смене JSON-библиотеки
  или фичи `preserve_order` паритет меток сломается (проверено 2026-11-22).

- ⚠️ **Список файлов в `npm test` — ЯВНЫЙ** (`package.json`), не glob →
  после удаления TS-модуля (`po2dat`, `prefill`, `find_source`, 2026-11-23)
  из списка надо убрать его тест, иначе `npm test` падает «файл не найден».
  Проверено: `verify` ловит это только на шаге `npm test`, поэтому после
  любой миграции — `npm test` первым.

- ⚠️ **Удалил эталон — добавь золото** → `po2dat`/`prefill`/`find_source`
  без TS-дублей, их выход заморожен в `scripts/golden/` и проверяется
  `scripts/text_golden.test.mts`. Для `potgen`/`po_update` эталоны удалены
  2026-11-24, золото — `test_data/pot-golden.json`,
  `test_data/pot-golden-small.pot`, `test_data/po-update-golden/`, страж —
  `scripts/text_parity.test.mts` и `tests/po_update.test.mts`. Обновление
  слепков остальных команд — только `GOLDEN_UPDATE=1 npm run test:golden`,
  чтобы дифф был осознанным. **Золото POT руками не «освежать»**: расхождение
  значит, что изменилось поведение Rust (политика/дедуп), и это надо доказать.

- ⚠️ **`pot_rules.mts` — не генератор, а правила проверок.** После удаления
  TS-эталонов 2026-11-24 в нём остались `buildCatalog`/`renderPot`/политики:
  их зовёт `scripts/pot_invariants.mts` (перегенерация `POT = дамп`) и
  `scripts/pot_provenance_report.mts`. Не добавлять сюда CLI/`scanDump`-прогон:
  единственная рабочая реализация генерации — Rust (`scripts/text_cli.mts`).
  Симптом ошибки: попытка «поправить POT» через TS-модуль в обход Rust.

- ⚠️ **Цвет разворачивался по мере сканирования → зависел от порядка файлов**
  (симптом: `<color=perversion>` вместо `#EB83FF` в `rich_text`, TMP цвет не
  понимает). Причина: `resolveNamedColors` вызывался при добавлении строки, а
  карта `color_parser_list` наполнялась позже. Лечение: второй проход после
  скана (Rust делает так же — `finish()`), тест в `inventory.test.mts`
  (проверено 2026-11-23). Диагностика — `npm run rich:audit`, класс
  `named-color` обязан быть 0.

- ⚠️ **Кривые теги в POT — это данные игры, а не наш парсер** → 210 незакрытых
  `<i>`, 12 перекрещенных, 4 лишних закрытия. TMP это терпит, текст ключа не
  страдает; «дочинить» = переписать контент. Разбор и цифры —
  `docs/rich-text-audit.md`; проверять `npm run rich:audit`, классы
  `self-fragment`/`malformed`/`unknown-tag` обязаны быть 0.

- ⚠️ **Обрывки `msgid` — не повод для skip, а повод починить ключ.** Игра (AN) получила `text`
  наивной чисткой `<[^>]+>`, авторские кавычки `< … >` съедены вместе с началом фразы; полный
  текст жив в `rich_text`. Проверено 2026-11-23 на `sharedassets7.jsonl` (pid 1205). Что делать:
  `buildCatalog` берёт полную фразу из `rich_text` (`#. repaired: <хвост>`); `fragment`-skip
  остаётся только страховкой. Страж — `scripts/fragment_repair.test.mts` (2 записи, 0 skip).

- ⚠️ **Save-ключи маскируются под текст.** `GlowingHoleKeys/103 Peeking Counter`,
  `CartelHideoutBadendKeys/Did get naked` — идентификаторы сохранений, не реплики; 85 живых
  записей (2026-11-23). Что делать: правило `saveKey` (префикс до `/` кончается на `Key(s)`);
  `24/7 Kiosk` и `Annoyed / Angry` правилом не задеваются — проверено тестом.

- ⚠️ **Где есть rich_text, должен быть rich_translation.** Для тегов ВНУТРИ фразы сборка
  `Replace` не работает, и без `rt` игрок видит перевод без цвета. Проверено 2026-11-23:
  `ru` 367/385, `de`/`pl` 0/287 (унаследованы без аннотаций), 18 строк не закрываются — перевод
  потерял междометие. Что делать: `npm run rt:audit` (+ `--strict` для релиза), заполнение —
  `npm run rt:pass -- --lang <l> --mode span`.

- ⚠️ **Snake_case ключи — имена ассетов, а не текст.** `CC_Option_Outfit_Futereswear Skintight
Suit Dark`, `Apl_Female_Carte_Suit2 Grey`, `PMA_IsNude` переводились как речь и давали гибрид
  («Апл_Женский_Карточный_Формат2», «CC_Option_Headgear_Tёмный бини»). Проверено 2026-11-23:
  415 живых записей с `\w_\w`, в диалогах — одна (путь к ассету). Что делать: правило
  `snake-case` (условие `snakeCase`, TS + Rust) — сняло 314 записей. Настоящие подписи для
  игрока приходят отдельным полем `field:DisplayName`, их правило не трогает.

- **Термин в диалогах живёт отдельно от `speaker-name`.** Канон `Enforcer → Силовик` есть в
  `msgctxt "speaker-name"`, но в тексте тот же термин переводился как «энфорсер», «исполнитель»,
  «преследователь», «стражник» (58 строк, 2026-11-23). Что делать: глоссарий в промпт теперь
  ставит канон первым (см. `buildGlossary`), а уже переведённое выравнивать поиском по
  английскому термину в `msgid`.

- ❌ **`#, legacy` — это инфошум, механизм удалён (решение владельца 2026-11-23).**
  Метка означала «ключ пропал из POT, держим перевод для рантайма». На замере в `ru`
  оказалось 597 таких записей: 128 давно вернулись в POT (флаг протух, потому что
  `po_update` копировал флаги как есть), 208 — `msgstr == msgid` или имена ассетов,
  262 — старый YAML-корпус без провенанса. Что делать: POT — единственный источник
  «что нужно игре»; сироты при слиянии **выпиливаются** с отчётом
  (`orphan_dropped`, `orphanItems` поимённо), а не копятся в хвосте PO. Если текст
  реально нужен игре — его место в POT, то есть чинится экстрактор, а не PO.
  Проверка: `po:update` на `ru` даёт `orphans=0`, в файле нет `^#, legacy`.

- ⚠️ **`tmp/pot-excluded.jsonl` — журнал ПОСЛЕДНЕГО прогона, а не накопительный.** После
  `potgen --update` в нём осталась одна строка, и сверка «что вырезала политика» показала
  ложную дыру в 125 507 строк (на деле — ассетный провенанс, вырезанный политикой). Проверено
  2026-11-23. Что делать: для аудита полноты POT сравнивать инвентарь с POT и отбирать по
  провенансу (как `tmp/pot_gap_visible.mts`), а журнал использовать только после свежего прогона.

- ⚠️ **Один и тот же текст у разных спикеров в `.dat` схлопывается.** Рантайм ищет по тексту,
  поэтому из 6 пар вроде `Yeah...` (Sarah «Да...», Zoey «Ага...») в патч попадает **один**
  вариант — `po2dat` печатает `DUPE`. Проверено 2026-11-23. Что делать: не считать такие
  строки независимыми; при вычитке выбирать вариант, нейтральный к персонажу.

- ❌ **`isUiString` резал описания и подсказки по «50 символам» — видный текст игры терялся.**
  Проверено 2026-11-24 на дампе `tmp/dump-after`: 11 `Description` (описания одежды, например
  «Business up top, party down below. Part of the Hi-Thread casual set.») и 5 `UnlockHint`
  (подсказки галереи, «Inspect Max's crotch.») не попадали в POT никогда: эвристика отсекала
  строки >50 code points и предложения с точкой. Что делать: для полей из `TEXT_FIELDS`
  (`Description`, `UnlockHint`, `m_text`, `DisplayName`, `UseText`, `TakenFromInventoryText`)
  фильтр `isUiString(s, trusted = true)` не применяет длину/точку/скобки/теги, потолок 500.
  Лейбл поля обязан вычисляться **до** фильтра (в TS и Rust одинаково — паритет `potgen`).
  Симптом в будущем: игровой текст виден в игре, но поиск по `msgid` в `po/*.po` пуст —
  сначала проверять дамп на доверенном поле, а не дописывать строку в PO руками.

- ❌ **Названия предметов резались правилом скобок и политикой `field:Name`.**
  Проверено 2026-11-24: 63 имени вида «Leather Skirt (Black)», «Sporty Bra (Black)»
  в базе предметов (`resources`) отбрасывались эвристикой `isUiString`, потому что
  содержат `(…)`; парные копии из бандлов проходили как `field:Name`, а эта метка
  в `config/pot-src-policy.json` исключена (имена объектов/анимаций). Что делать:
  имя опознаётся СТРУКТУРНО — в raw-куче оно стоит сразу за своим id `Apl_<…>`;
  такие строки получают метку `field:ItemName` (синтетическая, в политике
  разрешена) и доверенный фильтр. Симптом в будущем: игрок видит название
  предмета, в `po/*.po` его нет — искать в дампе пару `Apl_…` + имя, а не
  добавлять строку в PO руками.
